# PoC 개발 계획: 에이전트 노출 점검

> 상태: 초안 (2026년 11월 12일)
> 기준 문서: [설계 문서: 에이전트 노출 점검](agent-exposure-check-design.md)
>
> 이 계획의 API 관련 내용은 일반적인 Android 지식에 근거하며 Android 17·One UI 8.5 실기기에서
> 검증하지 않았다. 검증이 필요한 항목은 0주차 작업으로 모았다.

## 1. PoC의 목적

PoC는 제품의 축소판이 아니라 **설계의 불확실한 부분을 확인하는 실험**이다. 아래 네 가지 질문에 답하면 끝난다.

| # | 질문 | 판정 기준 |
|---|---|---|
| Q1 | 폰에서 에이전트를 신호 기반으로 가려낼 수 있는가 | 시험 기기에 설치한 에이전트·비에이전트 앱 세트에서 정밀도·재현율 측정 |
| Q2 | "데이터 단위 표시"가 권한 화면보다 사용자에게 더 유용한가 | 5~8명 사용성 테스트에서 "내 신분증 사진을 볼 수 있는 앱은?" 같은 과제의 정답률·소요 시간 비교 |
| Q3 | 기기 안에서 민감 항목을 쓸 만한 정확도와 비용으로 분류할 수 있는가 | 범주별 정밀도·재현율, 사진 1,000장 기준 처리 시간과 배터리 소모 |
| Q4 | 일반 앱 권한으로 보이지 않는 것은 무엇인가 | 시스템 권한이 있어야만 얻을 수 있는 정보의 목록. 시스템 기능 요구사항의 근거가 된다 |

## 2. 전제와 범위

### 전제

- **PoC는 일반 설치 앱(사이드로드)으로 만든다.** 플랫폼 서명이나 시스템 이미지 수정 없이 시작한다.
  누구나 시험 기기에서 돌려볼 수 있고, Q4에 답하려면 일반 권한의 한계를 직접 확인해야 하기 때문이다.
- 일반 권한으로 안 되는 부분은 **ADB 권한 계층**(개발자 옵션으로 얻는 셸 권한)으로 보완한다.
  이 계층에서 얻은 정보는 화면에 "시스템 권한 필요"로 구분해 표시한다.
- Personal Data Engine에는 접근할 수 없다고 가정하고, 로컬 DB로 대체한다.
- 플랫폼 서명 빌드를 쓸 수 있다면 4단계(선택)에서 시스템 권한 버전을 추가한다.

### 범위

| 설계 문서 항목 | PoC 포함 여부 |
|---|---|
| 에이전트 식별 (4.1) | 포함 |
| 접근 범위 수집 (4.2) | 포함. AppFunctions와 처리 위치는 부분 구현 |
| 민감도 분류 (4.3) | 신분 증명, 인증 정보, 금융 3개 범주만 |
| 화면을 읽는 에이전트 처리 (4.4) | 앱 단위 표시만 |
| 위험 점수 (6장) | 단순 버전 |
| 화면 (7장) | 요약, 에이전트 목록·상세, 데이터 기준 보기 |
| 조치 (8장) | 해당 설정 화면으로 이동까지. 직접 회수는 ADB 계층에서만 |
| 변화 감시 | 주기적 스냅샷 비교 |
| KEEP·Knox Vault 저장 | 제외. 앱 전용 암호화 DB로 대체 |

### 비범위

- Play 스토어 배포, 다국어, 접근성 대응, 디자인 완성도
- 클라우드 커넥터 점검
- 실행 중 공격 탐지

## 3. 기술 구성

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어·UI | Kotlin, Jetpack Compose | 표준 구성 |
| 저장 | Room (SQLite) + SQLCipher | 설계 문서의 데이터 모델을 테이블로 옮김. 색인 암호화 |
| 백그라운드 | WorkManager | 주기 스캔과 스냅샷 비교 |
| 텍스트 인식 | ML Kit Text Recognition (기기 내, 한국어) | 사진·스크린샷 속 텍스트 추출 |
| 텍스트 분류 | 정규식 + 검증식 | 주민등록번호 형식, 카드번호 Luhn 검사, 인증번호 문구 패턴 |
| 이미지 분류 | 경량 TFLite 분류기 | 신분증·여권·카드·통장 사본 판별 |
| 권한 보완 | ADB 권한 계층 (Shizuku 등) | 셸 권한으로 시스템 API 호출 |
| 대상 기기 | Galaxy S25/S26 (One UI 8.5), Android 17 에뮬레이터 | 삼성 실기기와 순정 Android 비교 |

저장소 구조:

```
poc/
  app/                 Android 앱
    collector/         에이전트 식별, 접근 경로 수집
    classifier/        민감도 분류
    risk/              위험 점수
    ui/                화면
    data/              Room 엔티티 (Agent, AccessPath, SensitiveItemGroup, Exposure, ChangeEvent)
  testdata/            합성 테스트 데이터와 생성 스크립트
  eval/                정확도·성능 측정 스크립트와 결과
```

## 4. 수집 방법과 권한 계층

각 정보를 어떤 계층에서 얻을지에 대한 가설이다. 0주차에 실기기에서 검증한다.

| 정보 | 일반 앱 | ADB 계층 | 시스템 권한 |
|---|---|---|---|
| 설치된 앱 목록과 요청·허용된 권한 | 가능 (전체 앱 조회 권한 선언 필요) | | |
| 활성화된 접근성 서비스 | 가능 | | |
| 알림 접근이 켜진 앱 | 가능할 것으로 예상 | 확실 | |
| 어시스턴트 역할 보유 앱 | 불확실 | 가능 | |
| 앱에 내장된 AI SDK | 가능 (APK 분석) | | |
| 사진 "선택 항목만" 허용 상태 | 가능 (권한 조합으로 판별) | | |
| 권한별 최근 실제 접근 시각 | 불가 | 가능 | |
| AppFunctions 등록 기능 목록 | APK 내 선언 파일 분석으로 일부 | 조회 가능한지 확인 필요 | 가능 |
| 화면 캡처 사용 중인 앱 | 불가 | 일부 | 가능 |
| 앱별 에이전트 자동화 허용 설정 | 불가 | 확인 필요 | 가능 |
| 다른 앱의 권한 직접 회수 | 불가 (설정 화면 이동만) | 가능 | 가능 |

AI SDK 탐지는 앱의 코드에서 알려진 SDK 패키지명을 찾는 방식이다. 추적기 탐지 도구(Exodus Privacy)나
라이브러리 분석 앱(LibChecker)이 같은 방식을 쓴다. 탐지 대상 목록은 온디바이스 추론 런타임과
주요 모델 제공사 SDK로 시작한다.

## 5. 일정

개발자 1~2명 기준 약 9주. 단계마다 종료 기준을 두고, 통과하지 못하면 다음 단계 전에 범위를 조정한다.

### 0주차: 검증 스파이크 (1주)

설계가 기대는 가정을 실기기에서 확인한다.

- 4장 표의 "불확실", "확인 필요" 항목을 Galaxy 실기기와 에뮬레이터에서 시험
- ADB 권한 계층이 Android 17·One UI 8.5에서 동작하는지 확인
- ML Kit 한국어 텍스트 인식을 신분증 샘플 이미지에 적용해 인식 품질 확인
- 시험용 에이전트 앱 세트 확정 (Gemini, Bixby, 서드파티 에이전트 앱, 접근성 기반 자동화 앱, 비에이전트 대조군)

종료 기준: 4장 표가 실측으로 갱신되고, 불가능한 항목의 대체 방법이 정해진다.

### 1단계: 권한 기반 지도 (3주)

설계 문서 1단계에 해당한다. 민감 데이터를 읽지 않는다.

| 주 | 작업 |
|---|---|
| 1 | 데이터 모델과 DB, 앱 목록·권한 수집기, 접근성·알림 접근 수집기 |
| 2 | 에이전트 식별 규칙, AI SDK 탐지, 권한 → 데이터 저장소 대응표 |
| 3 | 요약·에이전트 목록·에이전트 상세 화면, 설정 화면 이동 조치, ADB 계층 연동(최근 접근 시각, 직접 회수) |

종료 기준:
- 시험 세트에서 에이전트 식별 정밀도·재현율 측정 완료 (Q1)
- 에이전트별 접근 경로가 한 화면에 표시된다
- 일반 계층과 ADB 계층의 정보 차이가 목록으로 정리된다 (Q4 중간 결과)

### 2단계: 데이터 단위 점검 (3주)

| 주 | 작업 |
|---|---|
| 4 | 합성 테스트 데이터 구축, 문자·알림 텍스트 분류기 (인증번호, 금융 알림) |
| 5 | 이미지 분류기 (신분증·여권·카드·통장), 텍스트 인식 결합, 사진첩 증분 스캔 |
| 6 | 노출 계산(접근 경로 × 민감 항목 묶음), 위험 점수, 데이터 기준 보기 화면, 노출 한 줄 표시 |

종료 기준:
- 3개 범주의 정밀도·재현율과 사진 1,000장 처리 시간·배터리 소모 측정 완료 (Q3)
- "에이전트 X가 신분증 사진 N장에 접근 가능" 형태의 표시가 동작한다
- 색인에 원본 내용이 저장되지 않음을 DB 검사로 확인한다

### 3단계: 변화 감시와 평가 (2주)

| 주 | 작업 |
|---|---|
| 7 | 주기적 스냅샷 비교로 신규 에이전트·권한 확대 감지, 알림, 변화 기록 화면 |
| 8 | 사용성 테스트 (Q2), 결과 정리, 시스템 기능 요구사항 목록 작성 (Q4) |

종료 기준: 1장의 네 질문 각각에 대한 답과 근거가 결과 보고서에 정리된다.

### 4단계 (선택): 시스템 권한 버전

플랫폼 서명 빌드를 쓸 수 있을 때만 진행한다.

- ADB 계층에 의존하던 수집을 시스템 API 직접 호출로 교체
- AppFunctions 등록 기능 목록 조회, 앱별 자동화 허용 설정 연동
- Personal Data Engine 연동 가능성 검토

## 6. 테스트 데이터

**실제 개인정보를 쓰지 않는다.** 분류기 학습과 평가는 모두 합성 데이터로 한다.

- 신분증·여권·카드 이미지: 가상의 인물 정보로 만든 견본 양식 이미지. 촬영 각도, 조명, 일부 가림을 변형
- 문자·알림: 인증번호, 카드 승인, 입출금 알림 문구를 실제 형식에 맞춰 생성
- 대조군: 영수증, 명함, 일반 문서 스크린샷처럼 신분증과 혼동되기 쉬운 이미지
- 시험 기기는 개인 계정이 없는 전용 기기를 쓰고, 합성 데이터만 넣는다

사용성 테스트 참가자의 실제 기기에서 돌릴 경우에는 결과가 기기를 떠나지 않도록 하고, 화면 녹화 없이
관찰 기록만 남긴다.

## 7. PoC 자체의 보안

이 앱은 넓은 권한을 요청하므로, 스스로가 설계 문서의 원칙을 지켜야 한다.

- 네트워크 권한을 선언하지 않는다. 분류 모델은 앱에 내장한다
- 색인에는 범주·위치·개수만 저장하고 원본 내용은 저장하지 않는다
- DB는 암호화하고 백업 대상에서 제외한다
- 민감 데이터를 읽는 2단계 기능은 명시적 동의 후에만 켜진다
- 로그에 민감 항목의 내용이나 파일 경로를 남기지 않는다

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| Android 17에서 일반 앱의 조회 범위가 예상보다 좁다 | 0주차에 확인. 좁다면 ADB 계층 의존도를 높이고 그 사실 자체를 Q4의 결과로 기록 |
| ADB 권한 계층이 최신 One UI에서 동작하지 않는다 | 0주차에 확인. 안 되면 PC에서 ADB 명령으로 수집한 결과를 앱이 읽는 방식으로 대체 |
| 신분증 분류기의 오탐이 많다 | 범주를 "신분증으로 보이는 문서"로 넓히고 사용자 확인 단계를 둔다. 오탐률을 결과로 보고 |
| 합성 데이터로 학습한 모델이 실제 사진에서 성능이 떨어진다 | PoC에서는 합성 데이터 성능만 주장하고, 실제 데이터 검증을 후속 과제로 명시 |
| 에이전트 식별 신호가 Gemini·Bixby 같은 시스템 에이전트를 놓친다 | 시스템 에이전트는 알려진 패키지 목록으로 보완 |
| AppFunctions를 지원하는 앱이 아직 적어 시험이 어렵다 | 시험용 앱을 직접 만들어 기능을 등록하고 조회되는지 확인 |

## 9. 산출물

- PoC 앱 소스와 설치 파일
- 합성 테스트 데이터와 생성 스크립트
- 결과 보고서: Q1~Q4의 답, 측정값, 사용성 테스트 결과
- 시스템 기능 요구사항 목록: 시스템 권한이 있어야만 가능한 항목과 필요한 내부 인터페이스
- 설계 문서 개정안

## 10. 시작 전에 정해야 할 것

- **플랫폼 서명 빌드 사용 가능 여부**: 가능하면 4단계를 일정에 넣고, ADB 계층 작업을 줄일 수 있다
- **시험 기기**: Galaxy S25 또는 S26 1대 이상, 개인 계정이 없는 전용 기기
- **인력**: 2단계의 이미지 분류기는 모델 학습 경험이 있는 사람이 필요하다
- **사용성 테스트 참가자 모집 방식**과 실제 기기 사용 여부
- **PoC 코드의 위치**: 이 저장소의 `poc/` 디렉터리에 둘지, 별도 저장소로 분리할지
