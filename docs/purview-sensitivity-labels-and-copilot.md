## 1. 왜 이 선례를 보는가

검토 중인 아이디어는 "개인정보를 스캔해 목록으로 보여주고, 사용자가 항목에 **차단** 또는 **확인 후 제공(HITL)**
라벨을 붙이면, 에이전트에 데이터가 넘어가는 시점에 그 라벨대로 집행한다"는 것이다.

Microsoft Purview는 같은 구조를 기업 문서에 대해 이미 운영하고 있다. 데이터에 라벨을 붙이고, 그 라벨을
근거로 AI(Copilot)가 내용을 쓰지 못하게 한다. 무엇이 되고 무엇이 안 되는지를 확인해 두면 설계의 기준점이 된다.

## 2. 요약

- **라벨만으로는 Copilot을 막지 못한다.** 막는 수단은 두 가지다. 라벨에 **암호화**를 걸어 사용 권한으로
  제한하거나, **DLP 정책**으로 특정 라벨이 붙은 항목의 처리를 제외한다.
- DLP로 제외된 항목은 **인용 목록에는 계속 나타나고, 내용만 쓰이지 않는다.** 존재 자체는 감춰지지 않는다.
- 집행 방식은 **차단뿐이다.** 사용자에게 물어보고 진행하는 HITL 단계는 확인한 문서 어디에도 없다.
- 집행 지점이 여러 군데라 빠지는 경로가 있다. 외부 커넥터 데이터, Teams 회의·채팅 라벨, 프롬프트에 직접
  올린 파일은 적용되지 않는다.
- 2026년 1~2월에는 라벨과 DLP가 설정된 메일을 Copilot이 요약한 버그가 있었다. **집행은 AI 서비스의
  구현에 의존하며, 그 구현이 틀리면 라벨은 지켜지지 않는다.**

## 3. 동작 방식

### 3.1 라벨이 하는 일

| 기능 | 내용 |
|---|---|
| 표시 | Office 앱에서 열린 파일의 라벨 이름과 콘텐츠 표시가 사용자에게 보인다. Copilot Chat은 응답과 인용에 사용한 출처 중 우선순위가 가장 높은 라벨을 표시한다 |
| 상속 | Word, PowerPoint, Outlook의 Copilot이 새로 만든 콘텐츠는 원본의 라벨을 물려받는다. 상속된 라벨은 수동으로 붙인 더 낮은 우선순위의 라벨을 대체한다 |
| 암호화 연동 | 라벨이 암호화를 적용하면 사용 권한(usage right)으로 Copilot의 동작이 갈린다 (3.2) |
| DLP 연동 | DLP 정책의 조건으로 라벨을 지정해 Copilot 처리를 제외한다 (3.3) |

Microsoft 문서는 라벨이 암호화를 적용하거나 DLP와 연결될 때 "추가 보호 계층"이 된다고 설명한다.
암호화가 없는 라벨만으로 Copilot이 제한된다는 문장은 없으며, 문서는 암호화를 적용하지 않는 라벨이 붙은
콘텐츠가 Copilot에 반환될 수 있는 사례를 든다. (명시적 문장이 아니라 문서 내용에서 읽어낸 것이다.)

### 3.2 암호화와 사용 권한

| 사용자의 권한 | Copilot의 동작 |
|---|---|
| VIEW와 EXTRACT 모두 있음 | 내용을 요약하고 응답에 쓸 수 있다 |
| VIEW만 있음 | 요약하지 않는다. 링크로만 가리킬 수 있다. 앱에서 그 파일을 열어 둔 상태에서도 Copilot을 쓸 수 없다 |
| 이중 키 암호화(DKE) | Copilot과 에이전트가 접근하지 못하며 결과에 나오지 않는다 |

- EXTRACT는 텍스트 복사 권한이다. Microsoft는 이 권한이 "Copilot이나 에이전트가 암호화된 콘텐츠의 텍스트를
  사용자에게 보여줄 수 있는지를 결정한다"고 설명한다.
- 이 방식은 AI 전용 통제가 아니다. **사람의 복사 권한을 AI에도 그대로 적용한 것**이라, 사람에게는
  복사를 허용하면서 AI만 막을 수는 없다. AI만 막으려면 DLP를 써야 한다.

### 3.3 DLP 정책으로 처리 제외

정책 위치의 이름은 "Microsoft Copilot, Copilot Chat, and Copilot Cowork"다.

| 항목 | 라벨 기반 제외 | 프롬프트의 민감 정보 유형 차단 |
|---|---|---|
| 상태 | 미리 보기 표시 없음 | 미리 보기, 순차 배포 중 |
| 대상 | 저장된 파일과 열려 있는 파일, 2025년 1월 1일 이후 발송된 메일 | 기본 제공·사용자 정의 민감 정보 유형이 든 프롬프트 |
| 적용 범위 | Microsoft 365 Copilot, Copilot Chat, Cowork, Word·Excel·PowerPoint의 Copilot | 같음 |
| 사용자에게 보이는 것 | 항목은 **인용에 계속 나타나지만** 내용은 응답에 쓰이지 않는다. 안내 링크가 달린 정책 팁이 표시된다 | 응답하지 않는다. 그 프롬프트는 내부·웹 검색에도 쓰이지 않는다 |

- Word·Excel·PowerPoint에서는 **파일을 여는 시점**에 정책을 평가한다. 작업 중에 라벨을 붙이면 다음에 파일을
  열 때부터 적용된다. 차단 라벨이 붙은 파일을 열면 Copilot 기능이 비활성화된다.
- 정책 변경이 반영되기까지 최대 4시간이 걸린다.
- 2026년 2월 메시지 센터 게시물(MC1234661)은 라벨이 붙은 Word·Excel·PowerPoint 파일을 **저장 위치와
  무관하게**(로컬 기기 포함) 차단하도록 확장한다고 알렸다. 이전에는 서버가 SharePoint·OneDrive 주소로
  라벨을 조회했기 때문에 그 두 곳에서만 집행되었고, 변경 후에는 Office 클라이언트가 라벨을 직접 읽어
  전달한다. 배포 완료 예정은 2026년 6월 말이었다. 이 게시물은 제3자 미러로 확인했고, 배포가 실제로
  끝났는지는 확인하지 못했다. 현재 Learn 문서는 로컬 저장소를 언급하지 않는다.

### 3.4 라벨은 누가 붙이는가

- 사용자가 직접 붙이거나, 민감 정보 유형과 학습형 분류기를 조건으로 한 **자동 라벨링 정책**이 붙인다.
- Microsoft는 사전 학습된 분류기를 서버 측 자동 라벨링(SharePoint, OneDrive, Exchange)에 쓸 수 있게 했고,
  정책을 켜기 전에 결과를 미리 보는 시뮬레이션 모드를 제공한다.
- 오래된 기밀 파일을 Copilot에서 떼어 놓으려면 분류기 → 자동 라벨 → DLP를 엮어야 하고, 분류기를 만들어
  다듬고 라벨링을 돌리는 데 몇 주가 걸릴 수 있다는 실무자 글이 있다.
- 이 항목은 검색 결과 요약에 근거한다.

## 4. 한계와 사고

### 4.1 적용되지 않는 경우

| 경우 | 내용 |
|---|---|
| 외부 출처 데이터 | 플러그인과 Graph 커넥터로 들어온 데이터의 라벨·암호화는 Copilot Chat이 인식하지 못한다 |
| Teams 회의·채팅 라벨 | 현재 인식되지 않는다 |
| 컨테이너 라벨 | Teams, SharePoint 사이트, 그룹에 붙인 라벨은 안의 항목에 상속되지 않는다 |
| 다른 조직의 라벨 | Copilot은 자기 조직의 라벨만 다룬다 |
| 사용자 정의 권한 | 이 방식으로 암호화된, 열려 있지 않은 SharePoint·OneDrive 문서에는 접근하지 못한다(예외 있음). 라벨 상속도 지원되지 않는다 |
| 프롬프트에 직접 올린 파일 | DLP가 검사하지 않는다 |
| 일정 초대 | DLP 라벨 기반 제외가 지원되지 않는다 |
| Channel Agent | DLP 정책으로 식별된 라벨 파일의 요약을 막을 수 없다 |
| 조건 결합 | 한 규칙 안에서 민감 정보 유형 조건과 라벨 조건을 함께 쓸 수 없다(같은 정책의 별도 규칙으로는 가능) |
| 정책 구성 | Copilot 위치는 사용자 지정 템플릿에서만 고를 수 있고, 고르면 그 정책의 다른 위치는 모두 꺼진다 |

Copilot Studio로 만든 에이전트는 지식 원본이 SharePoint일 때 Copilot 위치의 DLP 정책으로 라벨 기반 제한이
가능하고, 암호화 지원도 SharePoint 지식 원본에 한정된다고 한다(검색 결과 요약 기준).
([Microsoft Learn: Copilot Studio](https://learn.microsoft.com/en-us/purview/ai-copilot-studio))

### 4.2 2026년 1~2월 사고 (CW1226324)

- Copilot의 "업무" 탭 채팅이 **기밀 라벨이 붙고 DLP 정책이 설정된 메일**을 요약했다. 대상은 사용자가 작성해
  Outlook 데스크톱의 보낸 편지함과 임시 보관함에 있던 메일이다.
- Microsoft는 1월 21일에 처음 탐지했고, 2월 18일에 보도로 알려졌다.
- 원인은 서비스 경고에서 "코드 오류"로만 설명되었다. 2월 초부터 수정이 배포되었고, 2월 20일 기준
  "대부분의 고객에 대해 근본 원인이 해결되었다"고 밝혔다. 영향 범위는 공개되지 않았다.
- Microsoft는 이 문제로 누구도 원래 권한이 없던 정보에 접근하게 되지는 않았다고 밝혔다.
- 이후의 최종 처리 결과는 확인하지 못했다.

## 5. 우리 아이디어에 주는 시사점

> 이 장은 조사 결과가 아니라 분석이다.

| Purview의 방식 | 우리 설계에 대한 함의 |
|---|---|
| 라벨 자체는 표시일 뿐이고, 집행은 암호화나 DLP가 한다 | 스캔과 라벨링만으로는 보호가 되지 않는다. 라벨을 읽고 판정하는 집행 지점을 따로 설계해야 한다 |
| 집행 방식은 차단뿐이다 | **HITL 단계는 이 선례에 없다.** 제공 시점에 사용자에게 묻는 부분은 새로 설계해야 하는 영역이다 |
| 제외된 항목이 인용에는 남는다 | "내용을 막는 것"과 "존재를 감추는 것"은 다른 결정이다. 신분증 사진이라면 존재가 드러나도 괜찮은지, 목록에서도 빼야 하는지를 라벨 종류로 구분할 필요가 있다 |
| 파일을 여는 시점에 평가하고, 정책 반영에 최대 4시간이 걸린다 | 라벨을 바꾼 직후의 공백이 생긴다. 한 기기 안에서 도는 시스템이라면 즉시 반영이 가능하므로 이 점은 유리하다 |
| 처음에는 SharePoint·OneDrive에서만 집행되다가 클라이언트가 라벨을 전달하도록 바뀌었다 | 집행 지점이 저장 위치에 묶이면 빠지는 경로가 생긴다. 라벨은 데이터와 함께 이동하거나, 모든 경로가 공통 판정 서비스에 물어야 한다 |
| 외부 커넥터, Teams 채팅, 직접 올린 파일은 적용되지 않는다 | 폰에서 대응되는 것은 서드파티 앱 안의 사본과 사용자가 에이전트에 직접 공유한 파일이다. 같은 구멍이 생긴다 |
| 사람의 복사 권한(EXTRACT)을 AI에 그대로 적용한다 | 폰에는 이미 앱 권한이 있지만, 에이전트 전용 통제는 권한과 별도의 층이어야 한다 |
| 수작업 라벨링은 규모가 안 맞아 자동 라벨링을 쓴다 | 항목별 라벨보다 **분류 단위 정책**(예: "신분증 사진은 차단")이 기본이어야 한다 |
| CW1226324: 라벨과 DLP가 설정되어 있었는데도 AI 서비스의 코드 오류로 무시되었다 | 집행을 에이전트 쪽 구현에 맡기면 안 된다. **데이터를 내주는 쪽**(삼성 앱과 프레임워크)에서 막아야 에이전트의 버그와 무관하게 지켜진다 |

## 6. 더 확인해야 할 것

- MC1234661의 배포 완료 여부와 로컬 파일 집행의 현재 상태
- 에이전트(Copilot Studio, Cowork, Channel Agent)별 라벨·DLP 적용 범위의 정확한 차이
- CW1226324의 최종 사후 보고서
- 암호화 없는 라벨이 Copilot을 제한하지 않는다는 점에 대한 Microsoft의 명시적 문장
- Purview에 사용자 확인(HITL)에 해당하는 동작(예: 사유 입력 후 재정의)이 Copilot 위치에도 있는지
