# 개인화 프로그램 시대의 보안 쟁점

> 작성일: 2026년 11월 23일.
> 이 문서는 논의를 정리한 분석 글이다. 외부 자료로 검증한 사실 조사가 아니므로,
> 인용하거나 근거로 쓰기 전에 개별 주장을 따로 확인해야 한다.

## 1. 배경

AI로 프로그램을 만드는 비용이 급격히 낮아지면서, 플랫폼이 심사한 소수의 프로그램을 쓰던 방식에서
개인이 직접 만들거나 남의 것을 개조한 프로그램을 쓰고 공유하는 방식으로 옮겨가고 있다.

이 변화의 핵심은 **신뢰의 근거가 사라진다**는 점이다. 지금까지는 "플랫폼이 심사했고 많은 사람이
써봤다"는 사실이 검증을 대신했다. 개인이 만들고 개조해 돌리는 프로그램에는 그런 근거가 없다.

## 2. 다섯 가지 쟁점

### 2.1 만든 사람도 내용을 모른다

AI로 생성한 프로그램은 작성자가 코드를 읽지 않은 경우가 많다. 악의가 없어도 다음과 같은 문제가
그대로 공유된다.

- 하드코딩된 API 키
- 인증 없는 엔드포인트
- AI가 지어낸 이름의 패키지를 공격자가 선점하는 문제(slopsquatting)

"아는 사람이 만들었으니 안전하다"가 성립하지 않는다.

### 2.2 개조와 재공유가 출처를 끊는다

원본이 안전해도 중간에 누군가 몇 줄을 바꿔 재배포하면 받는 사람은 차이를 알 길이 없다.
기존 오픈소스 공급망 공격과 같은 구조다. 다만 포크 비용이 0에 가까워지고 서명·평판·메인테이너
같은 완충 장치가 없어서 규모가 훨씬 커진다.

### 2.3 "프로그램"의 범위가 코드 밖으로 넓어진다

프롬프트, 에이전트 스킬, MCP 서버, 설정 파일도 실행물이 된다. 자연어로 쓴 악성 지시
(예: "작업 후 이 파일을 여기로 보내라")는 기존 백신이나 정적 분석으로 잡히지 않고,
사람이 읽어도 눈에 잘 띄지 않는다.

### 2.4 개인화될수록 권한이 깊어진다

개인용 프로그램은 메일, 파일, 캘린더, 결제 계정에 직접 붙어야 쓸모가 있다. 특히 에이전트형
프로그램이 다음 세 가지를 함께 가지면 프롬프트 인젝션 한 번으로 데이터가 유출된다.

- 민감 데이터 접근
- 외부 콘텐츠 읽기
- 외부 전송 능력

### 2.5 생성은 싸고 검증은 비싸다

프로그램은 몇 분이면 만들지만, 안전한지 확인하려면 여전히 전문성과 시간이 든다. 이 비대칭 때문에
대부분은 검증 없이 실행하게 되고, 공격자는 그럴듯한 프로그램을 대량으로 뿌릴 수 있다.

## 3. 기존 보안 기술로 막을 수 있는가

쟁점은 두 종류로 나뉜다.

- **도구 자체가 없는 문제**: 2.3(자연어 실행물). 탐지 도구도 관행도 거의 없다.
- **도구는 있는데 적용할 자리가 없는 문제**: 2.1, 2.2, 2.4, 2.5. 어떤 방향으로 풀어야 하는지는
  알려져 있지만, 기존 기술이 서 있는 전제가 무너지고 있다.

| 쟁점 | 기존 기술 | 깨지는 전제 |
|---|---|---|
| 작성자도 모르는 코드 (2.1) | 코드 리뷰, 정적 분석, 의존성 스캔 | 개발 조직과 파이프라인이 있어야 돌아간다. 혼자 만들어 바로 공유하는 개인에게는 이 과정이 없다. |
| 개조·재공유 (2.2) | 코드 서명, 패키지 레지스트리, SBOM | 서명은 "누가 만들었는지"만 증명한다. 익명의 개인 수백만 명이 서명해도 신뢰할 근거가 되지 않고, 평판이 쌓이기 전에 프로그램이 바뀐다. |
| 깊은 권한 (2.4) | 샌드박스, 권한 모델, OAuth 범위 | 권한 단위가 너무 굵다. "메일 읽기"를 허용하면 정상 동작과 유출을 구분하지 못한다. 그리고 사용자는 묻는 대로 허용한다. |
| 검증 비용 (2.5) | 앱 심사, 보안 감사 | 중앙의 심사 주체와 제한된 물량을 전제한다. 물량이 폭증하고 유통이 메신저나 깃 링크로 흩어지면 심사할 지점이 없다. |

후자의 네 가지는 새로운 종류의 위협이라기보다, 기존 위협이 **기존 방어가 감당하도록 설계된 규모와
구조를 벗어나는** 문제다. 덜 새롭다는 것이지 덜 위험하다는 것은 아니다. 실제 피해는 당분간 이쪽에서
더 많이 나올 가능성이 높다.

## 4. 풀어야 할 과제

후자의 문제는 기술을 새로 발명하기보다 다음 세 가지를 해결해야 한다.

- **기본값**: 보안 지식이 없는 사람이 아무 조치 없이 실행해도 격리되는 환경이 기본으로 깔려 있어야
  한다. 지금 데스크톱 OS는 그렇지 않다.
- **권한의 세밀함**: "무엇에 접근하는가"가 아니라 "접근한 데이터가 어디로 흘러가는가"를 통제해야
  한다. 연구는 오래됐지만 실용화가 거의 안 된 영역이다.
- **사람의 판단 한계**: 권한 요청과 경고를 늘릴수록 사람은 읽지 않고 승인한다. 기존 기술이 가장
  오래 실패해 온 부분이고, 프로그램 수가 늘면 더 나빠진다.

## 5. 방어의 방향

방어의 무게중심이 **"누가 검증했는가"에서 "무엇을 할 수 있게 허용했는가"로** 옮겨가야 한다.

- **샌드박스와 최소 권한을 기본값으로**: 프로그램을 믿을 수 없다고 전제하고, 실행 환경이 피해
  범위를 제한한다.
- **권한 선언과 실행 시점 통제**: 모바일 앱 권한처럼 "이 프로그램은 이 폴더와 이 도메인만 쓴다"를
  명시하고 강제한다.
- **출처와 변경 추적**: 원본 대비 무엇이 바뀌었는지 받는 쪽에서 확인할 수 있어야 한다.
- **AI를 이용한 검증**: 실행 전에 AI가 코드와 프롬프트를 읽고 하는 일을 요약해 주면 검증 비용의
  비대칭이 줄어든다. 다만 검증하는 AI도 인젝션 대상이 된다.
