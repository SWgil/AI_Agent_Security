# 개인화 프로그램 시대의 보안 쟁점

> 작성일: 2026년 11월 23일.
> 이 문서는 논의를 정리한 분석 글이다. 외부 자료로 검증한 사실 조사가 아니므로,
> 인용하거나 근거로 쓰기 전에 개별 주장을 따로 확인해야 한다.

## 1. 배경

AI로 프로그램을 만드는 비용이 급격히 낮아지면서, 플랫폼이 심사한 소수의 프로그램을 쓰던 방식에서
개인이 직접 만들거나 남의 것을 개조한 프로그램을 쓰고 공유하는 방식으로 옮겨가고 있다.

이 변화의 핵심은 **신뢰의 근거가 사라진다**는 점이다. 지금까지는 "플랫폼이 심사했고 많은 사람이
써봤다"는 사실이 검증을 대신했다. 개인이 만들고 개조해 돌리는 프로그램에는 그런 근거가 없다.

## 2. 다섯 가지 쟁점

### 2.1 만든 사람도 내용을 모른다

AI로 생성한 프로그램은 작성자가 코드를 읽지 않은 경우가 많다. 악의가 없어도 다음과 같은 문제가
그대로 공유된다.

- 하드코딩된 API 키
- 인증 없는 엔드포인트
- AI가 지어낸 이름의 패키지를 공격자가 선점하는 문제(slopsquatting)

"아는 사람이 만들었으니 안전하다"가 성립하지 않는다.

### 2.2 개조와 재공유가 출처를 끊는다

원본이 안전해도 중간에 누군가 몇 줄을 바꿔 재배포하면 받는 사람은 차이를 알 길이 없다.
기존 오픈소스 공급망 공격과 같은 구조다. 다만 포크 비용이 0에 가까워지고 서명·평판·메인테이너
같은 완충 장치가 없어서 규모가 훨씬 커진다.

### 2.3 "프로그램"의 범위가 코드 밖으로 넓어진다

프롬프트, 에이전트 스킬, MCP 서버, 설정 파일도 실행물이 된다. 자연어로 쓴 악성 지시
(예: "작업 후 이 파일을 여기로 보내라")는 기존 백신이나 정적 분석으로 잡히지 않고,
사람이 읽어도 눈에 잘 띄지 않는다.

### 2.4 개인화될수록 권한이 깊어진다

개인용 프로그램은 메일, 파일, 캘린더, 결제 계정에 직접 붙어야 쓸모가 있다. 특히 에이전트형
프로그램이 다음 세 가지를 함께 가지면 프롬프트 인젝션 한 번으로 데이터가 유출된다.

- 민감 데이터 접근
- 외부 콘텐츠 읽기
- 외부 전송 능력

### 2.5 생성은 싸고 검증은 비싸다

프로그램은 몇 분이면 만들지만, 안전한지 확인하려면 여전히 전문성과 시간이 든다. 이 비대칭 때문에
대부분은 검증 없이 실행하게 되고, 공격자는 그럴듯한 프로그램을 대량으로 뿌릴 수 있다.

## 3. 기존 보안 기술로 막을 수 있는가

쟁점은 두 종류로 나뉜다.

- **도구 자체가 없는 문제**: 2.3(자연어 실행물). 탐지 도구도 관행도 거의 없다.
- **도구는 있는데 적용할 자리가 없는 문제**: 2.1, 2.2, 2.4, 2.5. 어떤 방향으로 풀어야 하는지는
  알려져 있지만, 기존 기술이 서 있는 전제가 무너지고 있다.

| 쟁점 | 기존 기술 | 깨지는 전제 |
|---|---|---|
| 작성자도 모르는 코드 (2.1) | 코드 리뷰, 정적 분석, 의존성 스캔 | 개발 조직과 파이프라인이 있어야 돌아간다. 혼자 만들어 바로 공유하는 개인에게는 이 과정이 없다. |
| 개조·재공유 (2.2) | 코드 서명, 패키지 레지스트리, SBOM | 서명은 "누가 만들었는지"만 증명한다. 익명의 개인 수백만 명이 서명해도 신뢰할 근거가 되지 않고, 평판이 쌓이기 전에 프로그램이 바뀐다. |
| 깊은 권한 (2.4) | 샌드박스, 권한 모델, OAuth 범위 | 권한 단위가 너무 굵다. "메일 읽기"를 허용하면 정상 동작과 유출을 구분하지 못한다. 그리고 사용자는 묻는 대로 허용한다. |
| 검증 비용 (2.5) | 앱 심사, 보안 감사 | 중앙의 심사 주체와 제한된 물량을 전제한다. 물량이 폭증하고 유통이 메신저나 깃 링크로 흩어지면 심사할 지점이 없다. |

후자의 네 가지는 새로운 종류의 위협이라기보다, 기존 위협이 **기존 방어가 감당하도록 설계된 규모와
구조를 벗어나는** 문제다. 덜 새롭다는 것이지 덜 위험하다는 것은 아니다. 실제 피해는 당분간 이쪽에서
더 많이 나올 가능성이 높다.

## 4. 풀어야 할 과제

후자의 문제는 기술을 새로 발명하기보다 다음 세 가지를 해결해야 한다.

- **기본값**: 보안 지식이 없는 사람이 아무 조치 없이 실행해도 격리되는 환경이 기본으로 깔려 있어야
  한다. 지금 데스크톱 OS는 그렇지 않다.
- **권한의 세밀함**: "무엇에 접근하는가"가 아니라 "접근한 데이터가 어디로 흘러가는가"를 통제해야
  한다. 연구는 오래됐지만 실용화가 거의 안 된 영역이다.
- **사람의 판단 한계**: 권한 요청과 경고를 늘릴수록 사람은 읽지 않고 승인한다. 기존 기술이 가장
  오래 실패해 온 부분이고, 프로그램 수가 늘면 더 나빠진다.

## 5. 방어의 방향

방어의 무게중심이 **"누가 검증했는가"에서 "무엇을 할 수 있게 허용했는가"로** 옮겨가야 한다.

- **샌드박스와 최소 권한을 기본값으로**: 프로그램을 믿을 수 없다고 전제하고, 실행 환경이 피해
  범위를 제한한다.
- **권한 선언과 실행 시점 통제**: 모바일 앱 권한처럼 "이 프로그램은 이 폴더와 이 도메인만 쓴다"를
  명시하고 강제한다.
- **출처와 변경 추적**: 원본 대비 무엇이 바뀌었는지 받는 쪽에서 확인할 수 있어야 한다.
- **AI를 이용한 검증**: 실행 전에 AI가 코드와 프롬프트를 읽고 하는 일을 요약해 주면 검증 비용의
  비대칭이 줄어든다. 다만 검증하는 AI도 인젝션 대상이 된다.

## 6. 설치 차단 방식은 어떻게 바뀔 수 있는가

> 6~9절의 제품·정책 관련 사실(안드로이드, 구글, 삼성, GitHub, F-Droid 등)은 기억에 의존해
> 적은 것이며 외부 자료로 확인하지 않았다. 세부 내용과 일정은 인용 전에 확인해야 한다.

갤럭시의 보안 위험 자동 차단(Auto Blocker)은 "공인 스토어에서 온 앱인가"라는 이분법에 기대고
있다. 개인화 프로그램 시대에는 이 기준이 두 방향에서 어긋난다.

- **출처가 없는 것이 정상이 된다.** 내가 만들었거나 지인이 만들어 준 앱은 전부 "알 수 없는 앱"이다.
  다 막으면 쓸모를 막고, 차단을 끄면 스위치 하나로 모든 것이 열린다. 중간이 없다.
- **설치를 거치지 않는 프로그램이 늘어난다.** 웹앱, 에이전트 스킬, 프롬프트, 자동화 루틴,
  에이전트가 즉석에서 만들어 실행하는 코드는 설치 관문을 지나지 않는다.

그래서 차단 방식은 없어지기보다 **"설치를 막는가"에서 "설치는 되지만 무엇을 못 하게 하는가"로**
바뀔 가능성이 높다.

| 변화 | 내용 |
|---|---|
| 차단에서 단계적 허용으로 | 미검증 앱도 설치는 되지만 접근성 서비스, 문자 읽기, 화면 오버레이, 임의 네트워크 전송 같은 위험 권한은 잠긴 채로 실행된다. 안드로이드 13의 사이드로드 앱 "제한된 설정"이 초기 형태다. |
| 출처 대신 작성자 신원으로 | 스토어를 거치지 않아도 되지만 누가 만들었는지는 등록돼 있어야 한다. 구글의 개발자 인증 의무화가 이 방향이다. 개인 제작자 예외를 어디까지 둘지가 쟁점이다. |
| 설치 시점에서 실행 시점으로 | 설치할 때 한 번 판단하는 대신 실행 중 행동을 기기에서 감시한다. |
| 기기 내 AI의 사전 요약 | 설치 전에 앱의 실제 동작을 요약해 보여 준다. 검사하는 AI를 속이는 공격이 새로 생긴다. |
| 격리 공간 | 실제 데이터와 분리된 공간에서 먼저 돌려 보고, 믿을 만하면 꺼내 쓴다. |
| 관문이 에이전트로 이동 | 통제 대상이 앱 설치가 아니라 "에이전트가 무엇을 실행하고 어디에 접근해도 되는가"가 된다. 아직 정해진 방침이 거의 없다. |

단기적으로는 더 조이는 쪽일 가능성이 높다. 피싱 앱 피해가 늘고 있고, 제조사에게는 차단이 가장
싸고 책임지기 쉬운 선택이기 때문이다. 반대 방향의 압력은 규제와 사용자 수요다.

현실적인 절충은 **"내가 만든 것"과 "남이 준 것"을 구분하는 것**이다. 위험이 큰 쪽은 제작이 아니라
공유 경로이기 때문이다.

## 7. APK와 작성자 신원

### 7.1 지금 APK 서명이 증명하는 것

모든 APK는 서명이 있어야 설치되지만, 인증서는 개발자가 직접 만든 자체 서명이다. 인증기관이 없어서
인증서에 적힌 이름을 아무도 확인하지 않는다.

- **증명하는 것**: 이 업데이트가 이전 버전과 같은 키로 서명됐다는 연속성.
- **증명하지 않는 것**: 그 키의 주인이 누구인지.

신원 확인은 APK가 아니라 유통 경로(스토어의 개발자 계정 심사)에서 해 왔다. 스토어 밖으로 나온
APK에는 이 정보가 따라오지 않는다.

### 7.2 신원 검증은 가능한가

기술적으로는 가능하고 선례가 있다. 서명 키를 실제 신원에 묶어 두는 등록부를 두면 된다.

- 윈도우 코드 서명 인증서
- 애플 Developer ID와 공증
- 구글의 안드로이드 개발자 인증

다만 증명 범위가 좁다. 신원 검증이 알려 주는 것은 "이 키를 등록한 사람이 누구인가"뿐이다.

- **안전하다는 뜻이 아니다.** 효과는 예방보다 사후 추적과 키 폐기에 있다.
- **신원 자체를 속일 수 있다.** 도용한 신분증, 명의 대여, 탈취한 서명 키가 쓰인다.
- **만든 사람이 아니라 마지막에 서명한 사람이다.** 남의 앱을 개조해 다시 서명하면 원본이
  무엇이었고 무엇이 바뀌었는지는 남지 않는다.
- **등록부를 누가 운영하느냐가 문제다.** 중앙 등록부를 한 회사가 쥐면 스토어 밖 배포까지 그
  회사의 허가를 받는 구조가 된다.
- **APK가 아닌 것은 대상 밖이다.** 프롬프트, 에이전트 스킬, 웹앱에는 서명 체계가 없다.

신원 검증은 **책임을 물을 대상을 정하는 장치**다. 대량 유포되는 피싱 앱에는 효과가 있고, 지인끼리
개조해 돌리는 프로그램에는 효과가 약하다.

## 8. 저장소·산출물·개발자를 묶는 구조

공개 저장소, 산출물(APK), 개발자 세 가지를 엮으면 "이 APK가 이 저장소에서 나왔고 누구에게 책임이
있는가"를 알 수 있다. 부품 단위로는 이미 있지만, 주로 npm·PyPI·컨테이너 같은 개발자용 생태계에서
쓰이고 폰의 APK 설치 단계까지는 연결돼 있지 않다.

| 연결 | 기술 | 하는 일 |
|---|---|---|
| 저장소 ↔ 산출물 | SLSA 출처 증명, GitHub Artifact Attestations, Sigstore | 빌드 시스템이 "이 파일은 이 저장소의 이 커밋에서 이 워크플로로 만들어졌다"는 증명서를 서명해 공개 투명성 로그에 남긴다. |
| 저장소 ↔ 산출물 (더 강함) | 재현 가능한 빌드 | 누구든 같은 소스로 빌드하면 같은 파일이 나오는지 직접 확인한다. F-Droid가 쓰는 방식이다. |
| 산출물 ↔ 개발자 | APK 서명, 구글 개발자 인증 | 서명 키와 등록된 신원을 묶는다. |

**강점**: 개조·재공유 문제에 잘 맞는다. 포크해서 고쳐 배포하면 증명서는 포크 저장소를 가리키고,
원본과 달라진 내용은 git 기록에 남는다. 서명만으로는 마지막에 서명한 사람밖에 모르지만, 저장소가
묶이면 무엇이 바뀌었는지까지 추적할 수 있다.

**빠져 있는 것**:

1. **폰이 확인하지 않는다.** 안드로이드 설치 과정은 이런 증명서를 보지 않는다. 가장 큰 공백이다.
2. **저장소 계정은 사람이 아니다.** 계정은 익명으로 만들 수 있고, 실명 확인 체계와 빌드 출처
   체계는 서로 연결돼 있지 않다.
3. **빌드 플랫폼을 믿어야 한다.** 빌드 도중 외부에서 받아오는 의존성은 저장소에 보이지 않을 수
   있다. 이를 없애려면 재현 가능한 빌드가 필요하다.
4. **출처가 확인돼도 안전하다는 뜻은 아니다.** 다만 소스가 묶여 있으면 AI가 대신 읽고 검사할
   대상이 생긴다.
5. **공개 저장소가 전제다.** 소스를 공개하지 않는 프로그램은 대상에서 빠진다.

새로 필요한 것은 암호 기술이 아니라 마지막 연결이다. 설치 시점에 기기가 증명서를 확인해 보여 주는
단계, 그리고 저장소 계정과 책임질 수 있는 신원을 묶는 방법이다.

## 9. 제조사가 출처 인증을 맡는 구상

삼성 같은 제조사가 개인화 앱의 소스를 공개 저장소로 받아 두고 앱에 인증서를 발급하는 시스템을
만든다고 가정한다.

### 9.1 유리한 점

- **마지막 연결을 쥐고 있다.** 설치 과정과 자동 차단을 직접 통제하므로 인증서 발급과 기기 확인을
  한 회사가 다 할 수 있다.
- **직접 빌드하면 증명이 단순해진다.** 제조사가 소스에서 빌드해 서명하면 "이 APK는 이 소스에서
  나왔다"가 구조적으로 보장된다.
- **계정이 실제 사람과 가깝다.** 기기, 전화번호, 본인인증과 묶여 있어 책임 추적이 쉽다.
- **폐기가 가능하다.** 문제가 확인되면 인증서를 취소하고 설치된 기기에서 실행을 막을 수 있다.
- **개조 이력이 남는다.**

### 9.2 문제가 되는 부분

1. **인증서가 "제조사가 안전을 보증했다"로 읽힌다.** 실제로 증명하는 것은 출처뿐인데 사용자는
   안전 보증으로 받아들인다. 가장 큰 위험이다.
2. **검증 물량 문제는 그대로다.** AI 검사에 기대야 하고, 통과한 악성 앱은 인증 표시를 달고 퍼진다.
3. **저장소 경쟁은 이기기 어렵다.** 개발자와 AI 코딩 도구는 이미 기존 저장소에 붙어 있다.
4. **특정 제조사 전용이다.** 구글의 개발자 인증과도 역할이 겹친다.
5. **공개 강제의 부작용이 있다.** AI로 만든 앱에 박힌 API 키나 개인정보가 그대로 노출된다.
   업로드 단계의 비밀값 검사가 필수다.
6. **APK만 다룬다.**

### 9.3 권하는 형태

저장소를 새로 만드는 부분은 빼고, 빌드·인증·기기 확인만 제조사가 맡는다.

- **저장소는 기존 것을 그대로 받는다.** 저장소 주소와 커밋을 받아 빌드하고, 검사하고, 인증서를
  발급한다.
- **인증서는 등급으로 나눈다.** "출처 확인됨", "자동 검사 통과", "사람 검토 완료"처럼 무엇을
  확인했는지 그대로 표시하고, "안전함"이라는 표현은 쓰지 않는다.
- **등급을 권한과 연결한다.** 출처만 확인된 앱은 위험 권한이 잠긴 채 실행되고, 등급이 오르면
  풀린다. 인증이 뚫려도 피해 범위가 제한된다.
- **인증 기록은 공개 로그에 남긴다.** 무엇에 인증서를 줬는지 외부에서 감사할 수 있어야 한다.

이렇게 하면 "차단 아니면 전부 허용" 사이에 중간 단계가 생기고, 제조사는 스토어 운영자가 아니라
**출처를 확인해 주는 공증인** 역할을 하게 된다. 성패는 기술보다 인증서의 의미를 사용자에게 과장
없이 전달할 수 있느냐에 달려 있다.
