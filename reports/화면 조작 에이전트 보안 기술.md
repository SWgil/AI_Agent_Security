# 화면 조작 에이전트 보안, 모델 바깥에서 결정된다

화면 조작 에이전트에 필요한 보안 기술의 핵심은 프롬프트 인젝션을 모델이 걸러 내는 기술이 아니라, **모델이 속더라도 피해 범위를 한정하는 기술**이다. 2026년 11월 현재 주요 벤더가 실제로 적용한 것은 다섯 겹이다. 격리 실행, 앱·사이트 허용목록, 로그인·결제 단계의 사람 확인 또는 인계, 2차 감시 모델과 인젝션 분류기, 실시간 표시와 활동 기록이다. 이 가운데 모델이 완전히 장악돼도 유지되는 것은 플랫폼이 강제하는 앞의 두 겹과 자격증명 분리뿐이고, 나머지는 벤더 스스로 확률적 방어라고 밝힌다. 앞으로 필요한 기술은 일곱 갈래로 정리된다. 화면을 보기 전에 계획을 고정하는 구조적 방어, 픽셀 대신 의미 단위로 행동하는 구조화 인터페이스, 실행될 행동에 묶인 신뢰 확인 화면, 스크린샷의 온디바이스 비식별화, 에이전트 신원·위임과 한도가 걸린 결제 토큰, 되돌리기와 변조 방지 로그, 메모리·스킬 공급망 무결성이다. 이들은 대부분 연구 또는 시범 단계이며, 모바일에서 평가된 구조적 방어는 찾지 못했다. 한국에서 쓰이는 갤럭시의 Gemini 화면 자동화는 가상 디스플레이, 특권 권한, 서버 배포 허용목록으로 보호되지만 Galaxy S26에서는 사용자가 작업을 넘겨받지 못하고 중지만 할 수 있다. 한국의 관련 규범(개인정보보호위원회 안내서, 금융보안원 평가기준)은 아직 초안 단계다. 출시된 폰 에이전트를 실제 보호 장치가 켜진 상태에서 적응형 공격으로 측정한 공개 평가는 없으므로, 벤더가 내놓은 수치는 보증이 아니라 자체 조건의 측정값으로 읽어야 한다.

이 보고서에서 "검색 요약"이라고 표시한 내용은 원문을 직접 열지 못하고 검색 결과 요약으로만 확인한 것이어서 수치와 표현의 신뢰도가 낮다. 표시가 없는 인용은 조사 시점(2026-11-18)에 해당 페이지를 직접 읽은 것이다. openai.com과 androidauthority.com은 접근이 차단되어 해당 내용은 2차 자료에 의존한다.

## 화면에 보이는 모든 것이 명령이 될 수 있다

화면 조작 에이전트가 API 호출형 에이전트보다 지키기 어려운 이유는 구조에 있다. 도구 호출형 에이전트는 도구 결과를 구분된 채널로 받지만, 화면 에이전트는 신뢰할 수 있는 시스템 UI, 사용자 본인의 데이터, 공격자가 쓴 콘텐츠가 한 장의 스크린샷 안에 같은 자격의 픽셀로 섞여 들어온다. 게다가 에이전트는 사용자가 로그인해 둔 모든 세션과 앱의 권한을 그대로 물려받는다. Brave는 Perplexity Comet 사례에서 이 점을 짚었다. Reddit 댓글에 숨긴 지시문이 "페이지 요약" 한 번으로 실행되어 사용자의 Gmail에서 OTP를 읽어 외부에 게시했고, Brave는 에이전트가 사용자 권한으로 움직이는 한 동일 출처 정책과 CORS가 "사실상 무용지물"이 된다고 설명했다 ([Brave](https://brave.com/blog/comet-prompt-injection/)). Google도 에이전트형 브라우저의 "주된 새 위협"을 간접 프롬프트 인젝션으로 규정한다 ([Google, 2025-12-08](https://blog.google/security/architecting-security-for-agentic/)).

화면 에이전트에만 있는 공격 유형도 확인된다. 첫째는 **사람과 모델이 서로 다른 화면을 보는 인식 격차**다. 공개 모바일 에이전트 프레임워크 5종을 대상으로 한 2026년 7월 연구는 불투명도 2%의 오버레이나 둥근 모서리·카메라 컷아웃 아래에 지시문을 넣었고, 사람 눈에는 보이지 않는 이 지시문을 모델이 20회 중 20회 또는 그에 가깝게 읽었다고 보고했다. 이 내용은 논문 원문이 아니라 Cloud Security Alliance(CSA) 연구 노트를 통해 확인했다 ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-mobile-agent-attack-surface-screen-injecti/)). 둘째는 **공격자가 밀어 넣는 입력**이다. SafeBreach는 WhatsApp·Slack·SMS 알림 한 통으로 Android의 Gemini에 지시를 주입해 장기 메모리를 오염시키고, 매일 저녁 메시지를 읽는 예약 작업을 심고, Google Home 기기까지 조작하는 시연을 공개했다. Google은 2025년 11월 서버 측 분류기 개선으로 완화했다고 확인했고, 실제 악용 증거는 보고되지 않았다. 다만 이 연구의 대상은 Gemini의 유틸리티(알림) 에이전트이며 화면 자동화 기능 자체가 아니다 ([The Hacker News, 2026-06](https://thehackernews.com/2026/06/whatsapp-slack-notifications-could.html)). 같은 연구는 확인 질문을 피해자가 모르는 언어로 띄우거나 음성 낭독이 건너뛰는 링크 텍스트에 숨겨, 사용자가 내용을 모른 채 승인하게 만드는 기법도 보였다. 사람의 확인 자체가 공격 대상이라는 뜻이다. 셋째는 캡처와 입력 경로에 대한 공격이다. 스크린샷 파일을 캡처와 전송 사이 평균 약 210ms 구간에 바꿔치기하거나, 투명 오버레이로 탭을 가로채는 방식이 여기에 속한다 ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-mobile-agent-attack-surface-screen-injecti/)).

측정된 공격 성공률은 세 구간으로 나누어 읽어야 한다. 논문마다 공격자 예산, 성공 기준, 모델 세대, 제품 보호 장치 적용 여부가 달라 수치를 서로 직접 비교할 수 없다. 제품 보호 장치 없이 구동한 에이전트는 여전히 크게 뚫린다. 실제 Android 앱 13개를 쓴 MobileWorldSafety(2026년 8월)에서 **Gemini-3-Pro 66.9%, Claude Sonnet 4.5 47.5%, MAI-UI-8B 40.4%**였고, 시스템 프롬프트 방어는 주로 에이전트를 멈추게 하는 방식으로만 수치를 낮췄다 ([arXiv 2608.17659](https://arxiv.org/html/2608.17659v1)). 고정된 수작업 인젝션에 대해서는 최신 모델의 브라우저 환경 수치가 한 자릿수 이하로 떨어진다. 한 단독 저자 프리프린트는 Claude Sonnet 4.6과 GPT-5.4에서 140회 중 0회를 보고했다 ([arXiv 2606.05233](https://arxiv.org/abs/2606.05233)). 그러나 공격자가 적응하면 다시 오른다. 자기 개선형 레드팀 SIR은 최대 10회 시도로 **Claude Opus 4.8에서 24%, Gemini 3.5 Flash에서 28%**를 기록했고, 같은 벤치마크의 고정 인젝션은 4%와 0%였다 ([arXiv 2608.30207](https://arxiv.org/abs/2608.30207)). 모바일 수치가 브라우저보다 한 세대 뒤처진다는 점도 드러난다. 방어 강화가 브라우저 표면에 집중되어 왔다는 해석과 맞는다.

실제 웹에서는 에이전트를 겨냥한 인젝션이 늘고 있다. Google은 월 20~30억 페이지를 스캔한 결과 악성 인젝션이 2025년 11월부터 2026년 2월 사이 상대적으로 32% 늘었다고 밝혔고, Forcepoint는 결제 기능을 가진 에이전트를 노린 PayPal 거래 페이로드를 발견했다. 다만 실제 에이전트에 대한 공격 성공이 확인된 사례는 보고되지 않았다 ([Help Net Security, 2026-04-24](https://www.helpnetsecurity.com/2026/04/24/indirect-prompt-injection-in-the-wild/)). 출시된 화면 조작 에이전트를 통해 실제 사용자가 피해를 본 확인된 사례도 조사 범위에서는 찾지 못했다. 지금까지의 "사고"는 연구자 개념 증명과 앱 측의 에이전트 차단이다.

## 출시된 방어는 다섯 겹이고, 모델이 뚫려도 버티는 것은 그 일부다

2026년 11월 기준 주요 벤더는 같은 패턴을 출시했다. 차이는 격리가 어디에 있느냐다. Google/Android(백그라운드 가상 디스플레이와 특권 권한), Microsoft(별도 OS 계정과 세션), 클라우드형 에이전트(원격 VM)는 플랫폼 수준에서 격리한다. 반면 Anthropic의 데스크톱 컴퓨터 사용은 도움말에서 "Claude와 애플리케이션 사이에 샌드박스가 없다"고 명시하고 권한과 모델 측 점검에 의존한다 ([Claude Help](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork)).

| 계층 | 출시된 사례 | 모델이 장악돼도 유지되는가 |
|---|---|---|
| 격리 | Android 가상 디스플레이, Windows 에이전트 전용 계정·세션, 원격 VM/브라우저(OpenAI, Gemini Agent), Brave 별도 프로필 | 유지된다. 단, 대상 앱 안에서는 사용자의 로그인 권한이 그대로다 |
| 범위 제한 | Google 서버 배포 앱 허용목록(세션당 최대 6개 앱), Chrome Agent Origin Sets, Edge 선별 사이트 목록, Claude 차단 앱·사이트와 관리자 목록 | 모델 밖에서 검사되는 한 유지된다. 허용된 앱·출처 안의 오용은 막지 못한다 |
| 사용자 동의·인계 | Android 시스템 대화상자와 앱별 "항상 허용/매번 묻기/허용 안 함", 구매·전송 전 확인, 로그인·결제 시 사용자 인계 | 시스템이 띄우는 동의는 유지된다. 모델이 판단해 묻는 확인은 유지되지 않는다 |
| 모델 수준 | Chrome User Alignment Critic과 인젝션 분류기, Anthropic 강화학습·분류기, OpenAI 감시 모델·적대적 학습, Edge Prompt Shields, Perplexity BrowseSafe | 유지되지 않는다(확률적) |
| 투명성·감사 | Android의 닫을 수 없는 알림 칩과 진행 보기, 삼성 "AI 어시스턴트 활동", Chrome 작업 로그 | 표시는 유지된다. 기록 주체(OS인지 어시스턴트 자기 보고인지)는 문서에 없다 |

이 표의 Android 항목은 개발자 문서와 Google 도움말 ([Android Developers](https://developer.android.com/ai/computer-control), [Pixel Phone Help](https://support.google.com/pixelphone/answer/16940971?hl=en)), Chrome 항목은 Chrome 보안팀 글 ([Google, 2025-12-08](https://blog.google/security/architecting-security-for-agentic/)), Windows 항목은 Microsoft 지원 문서 ([Microsoft Support](https://support.microsoft.com/en-us/windows/ai/ai-features/experimental-agentic-features))에 근거한다. OpenAI의 원격 브라우저, 인계 모드, 감시 모델은 원문 접근이 막혀 검색 요약으로만 확인했다 ([OpenAI](https://openai.com/index/introducing-operator/)). 독립 테스트에서는 Atlas의 Watch Mode가 GitHub와 온라인 뱅킹 사이트에서 작동하지 않았다는 보고도 있다 ([Simon Willison, 2025-10-22](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)).

브라우저에서는 Chrome의 설계가 가장 구체적으로 공개되어 있다. 계획 모델과 분리된 User Alignment Critic은 페이지 내용이 아니라 제안된 행동의 메타데이터만 보고 거부권을 행사한다. 에이전트가 읽을 수 있는 출처와 조작할 수 있는 출처는 별도의 게이팅 함수가 정한다. 은행·의료 사이트 이동 전 확인은 결정적 목록으로 이루어지고, 비밀번호는 모델에 전달되지 않는다. 그러나 Google은 처음에는 읽기-쓰기 집합만 추적하는 "더 단순한 버전"의 출처 게이팅을 구현했고 분류기가 "모든 것을 잡아낼 수는 없다"고 적었다 ([Google, 2025-12-08](https://blog.google/security/architecting-security-for-agentic/)). Anthropic은 Claude in Chrome에서 구매·금융 거래, 계정 생성, 카드·신분증 정보 처리, "이메일이나 웹 콘텐츠에 담긴 지시의 수행"을 권한 설정과 무관하게 금지 행동으로 둔다 ([Claude Help](https://support.claude.com/en/articles/12902446-manage-claude-in-chrome-permissions)).

### 갤럭시의 Gemini 화면 자동화: 플랫폼이 막는 것과 Gemini가 "노력하는" 것

갤럭시에서 앱 화면을 조작하는 에이전트는 Android Computer Control 프레임워크 위에서 동작하는 Google Gemini이므로, 격리와 동의는 Google의 장치다. 이 기능은 **한국을 포함한 5개국(인도, 일본, 한국, 영국, 미국)**에서 한국어·영어·일본어로 제공되며, 대상 기기는 Galaxy S26 시리즈, Z Flip 8, Z Fold 8, Tab S12 시리즈와 Pixel 10·11이다. 만 18세 이상의 개인 계정에서만 쓸 수 있고 베타 단계다 ([Pixel Phone Help](https://support.google.com/pixelphone/answer/16940971?hl=en)).

플랫폼이 강제하는 장치는 네 가지다. 에이전트가 되려면 특권 권한 `ACCESS_COMPUTER_CONTROL`이 필요하고, 이 권한은 OEM이 선탑재한 어시스턴트에만 주어진다. 대상 앱은 캐스팅과 유사한 백그라운드 가상 디스플레이에서 실행된다. 세션은 한 번에 하나이며 최대 6개 앱까지 포함한다. 세션 요청 시 프레임워크가 시스템 동의 대화상자를 띄운다 ([Android Developers](https://developer.android.com/ai/computer-control)). 여기에 Google이 서버에서 내려보내는 대상 앱 허용목록이 더해진다. 2차 매체에 따르면 2026년 11월 12일 기준 안정 버전 114개와 테스트 중 20개가 있고, 항목마다 앱 ID와 서명 인증서가 짝지어져 있으며, 음식·차량 호출·여행·쇼핑·업무 앱 위주이고 은행 앱은 언급되지 않는다 ([tech-ish, 2026-11-16](https://tech-ish.com/2026/11/16/gemini-task-automation-galaxy-apps/)). 원 출처인 Android Authority 기사는 접근이 차단되어 직접 확인하지 못했다. **한국의 금융·결제·메신저 앱이 이 목록에 있는지, 그 앱들이 화면 자동화를 탐지하거나 차단하는지는 확인된 자료가 없다.**

그 밖의 보호는 에이전트의 행동 방식에 속한다. 도움말은 Gemini가 메시지 전송이나 배송지 변경 같은 행동 전에 검토를 요청하는 것을 "목표로 한다(aims to)"고 쓰고, 주문 확정 같은 마지막 단계는 사용자가 수행하게 하며, 결제 정보 입력·로그인·계정 생성에서는 인계를 요청할 수 있다고 설명한다. 같은 문서는 사용자가 "구매 같은 예상치 못한 결과를 포함해 작업 중 Gemini의 행동에 책임이 있다"고 밝히고, 앱 콘텐츠나 이메일의 숨은 지시가 주문·주소 변경·메시지 전송을 일으킬 수 있다고 경고한다 ([Pixel Phone Help](https://support.google.com/pixelphone/answer/16940971?hl=en)). 프레임워크는 인계라는 기본 기능만 제공한다. 결제 직전에 멈추는 것은 프레임워크 규칙이 아니라 에이전트의 동작으로 보인다. 어떤 행동이 확인 대상인지 열거한 Google 문서는 찾지 못했다.

갤럭시 사용자가 알아야 할 구체적 한계는 세 가지다. 첫째, **Galaxy S26과 Pixel 10에서는 "제어권 가져오기"가 제공되지 않아 중지만 가능**하다. Z Flip 8과 Z Fold 8에서는 인계 요청 후 10분 안에 사용자가 넘겨받지 않으면 Gemini가 멈춘다 ([Pixel Phone Help](https://support.google.com/pixelphone/answer/16940971?hl=en)). 둘째, 삼성 One UI 9의 "AI 어시스턴트 활동"은 최근 24시간과 7일의 타임라인을 보여 주는 조회 전용 화면이다. 삼성 지원 페이지에는 삭제, 내보내기, 차단 기능이 없다 ([Samsung Support](https://www.samsung.com/in/support/mobile-devices/how-to-use-ai-assistant-activity-feature-in-galaxy-devices/)). 에이전트 통제를 Knox 기능으로 설명한 자료도 찾지 못했다. 셋째, 일일 요청 한도와 동시 작업 한도는 있으나 수치가 공개되지 않았고, 화면 자동화의 스크린샷 보존·검토 정책은 조사에서 읽은 페이지에 없었다. Google이 2026년 5월에 예고한 Android 프라이버시 대시보드의 AI 활동 보기는 당시 "곧"이라고만 했고, 안정 버전 출시 여부는 확인하지 못했다 ([Google, 2026-05-12](https://blog.google/security/android-gemini-intelligence-security-privacy/)).

제3자 에이전트에는 이 보호 경로가 열려 있지 않다. Google Play 접근성 API 정책은 "자율적으로 행동을 개시·계획·실행하는 앱"에 접근성 API를 쓰는 것을 금지한다 ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/16585319)). 따라서 순정 Android에서 화면 조작은 사실상 OS 벤더와 OEM 어시스턴트의 몫이 된다. 접근성 API 기반 오픈소스 에이전트는 측정된 위험이 크다. MobileRun과 Mobile-Use는 알림, 오버레이, 숨은 접근성 메타데이터로 탈취되었고 종합 공격 성공률은 프레임워크와 모델에 따라 0.15~0.82였다 ([arXiv 2608.08939](https://arxiv.org/html/2608.08939v1)). 기업 환경에서는 Android 17이 관리 기기의 AI 자동화를 통째로 끄는 설정과 업무 프로필 격리를 제공한다 ([Android Enterprise Community, 2026-06-16](https://www.androidenterprise.community/product-updates/android-17-brings-intelligent-experiences-and-advanced-safeguards-for-enterprise-2705)). 앱별 정책, 스크린샷 DLP, 감사 로그 내보내기는 조사한 자료에 문서화되어 있지 않다.

### 벤더들이 직접 밝힌 잔여 위험

모든 주요 벤더가 자사 문서에서 프롬프트 인젝션이 미해결임을 인정한다. 정량 수치를 공개한 곳은 조사 범위에서 Anthropic뿐이다. 2025년 11월 내부 적응형 공격자(환경당 100회 시도) 기준으로 Claude in Chrome의 공격 성공률은 Opus 4.5에서 모델 단독 8.0%, 개선된 보호 장치 적용 시 1.4%였다. Anthropic은 "1%도 여전히 의미 있는 위험"이라고 썼다 ([Anthropic, 2025-11-24](https://www.anthropic.com/research/prompt-injection-defenses)). 감소분의 대부분이 모델이 아니라 분류기와 행동 게이트 같은 시스템 계층에서 나온다는 점이 중요하다. 2026년 7월 시스템 카드의 "브라우저 0%" 수치는 2차 보도로만 확인했고, 컴퓨터 사용 수치는 출처 간에 상충하므로 확정된 값으로 인용할 수 없다 ([The Decoder](https://the-decoder.com/opus-5-may-have-solved-browser-based-prompt-injection-the-biggest-security-flaw-haunting-ai-agents/)). OpenAI는 프롬프트 인젝션이 "완전히 해결될 가능성이 낮다"고 했고 Atlas 강화 업데이트의 효과 수치는 공개하지 않았다(검색 요약) ([TechCrunch, 2025-12-22](https://techcrunch.com/2025/12/22/openai-says-ai-browsers-may-always-be-vulnerable-to-prompt-injection-attacks/)). 독립 벤치마크 RedTeamCUA에서 가장 큰 감소 효과를 보인 것은 사람 확인이었다. Operator의 공격 성공률은 확인·안전 점검을 끄면 30.89%, 켜면 7.57%였다 ([arXiv 2505.21936](https://arxiv.org/html/2505.21936v4)).

## 다음 세대 방어는 픽셀을 의미 있는 행동으로 바꾸는 데서 시작한다

탐지와 모델 강화만으로는 부족하다는 근거는 분명하다. OpenAI, Anthropic, Google DeepMind 연구자들이 함께 쓴 "The Attacker Moves Second"는 발표된 방어 12종을 적응형 공격으로 시험해 대부분에서 90%가 넘는 공격 성공률을 얻었다. 이 수치는 논문 원문이 아니라 검색 요약과 Simon Willison의 정리로 확인했다 ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023), [Willison](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). 그래서 연구의 무게는 모델이 뚫려도 성립하는 구조적 보증으로 옮겨 갔다. 문제는 그런 방어가 `send_email(to=...)`처럼 의미를 가진 타입 있는 행동과 출처를 식별할 수 있는 데이터를 전제한다는 점이다. 좌표 (x, y)의 탭에는 의미가 없고 스크린샷은 출처 라벨을 붙일 수 없는 한 덩어리다. 아래 표는 미래 기술을 성숙도와 함께 정리한 것이다.

| 기술 | 해결하려는 문제 | 성숙도 | 확인된 한계 |
|---|---|---|---|
| Rule of Two, 설계 패턴 | 신뢰할 수 없는 입력, 민감 데이터 접근, 상태 변경 가운데 최대 둘만 허용 | 설계 원칙으로 지금 적용 가능 | 세션 단위 규칙이어서 에이전트 간 전파는 막지 못한다 |
| 화면을 보기 전 계획(Single-Shot Planning) | 주입된 지시가 제어 흐름을 바꾸지 못하게 함 | 연구(브라우저·데스크톱만) | 데이터 흐름은 무방비, 성능 손실, 모바일 평가 없음 |
| 정보 흐름 제어·정책 모니터(FIDES, Progent 등) | 출처 라벨과 결정적 정책으로 행동 차단 | 도구 호출형에서 연구~실험 | GUI·모바일 평가 없음 |
| 구조화 인터페이스(AppFunctions, App Intents, MCP/A2A) | 픽셀 대신 선언된 기능 호출 | 시범~일부 출시 | 인젝션이 도구 설명·출력으로 옮겨 간다 |
| 행동에 묶인 신뢰 확인 화면 | 사용자가 본 내용과 실행 내용의 일치 | 연구 | 승인 폭주 공격이 남는다 |
| 온디바이스 스크린샷 비식별화 | 과제와 무관한 민감 정보의 클라우드 전송 차단 | 연구 | 소규모·합성 벤치마크 결과뿐 |
| 에이전트 신원·위임·결제 토큰 | 에이전트 식별, 한도가 걸린 권한 | 표준 초안~시범 | 사용자 세션으로 탭하는 온디바이스 에이전트에는 적용되지 않는다 |
| 되돌리기, 변조 방지 로그 | 사고 후 복구와 책임 입증 | 연구·원칙 선언 | 소비자용 출시 사례 없음 |
| 메모리·스킬 공급망 무결성 | 일회성 인젝션의 영구화 방지 | 초기 | 신뢰 기반 방어가 메모리의 효용을 없앤다 |

**구조적 방어의 현재 위치.** CaMeL 계열을 컴퓨터 사용 에이전트로 옮긴 유일한 본격 시도는 "CaMeLs Can Use Computers Too"(2026년 3월 개정)다. 특권 계획 모델이 화면을 보기 전에 조건 분기를 포함한 전체 실행 그래프를 만들고, 격리된 비전 모델이 좁은 도구로만 화면을 읽는다. 저자들은 임의의 지시 주입에 대한 제어 흐름 무결성을 주장하지만 데이터 흐름은 "여전히 취약"하다고 밝힌다. 광고 안의 가짜 쿠키 배너나 최적화된 픽셀로 승인된 계획의 정상 분기를 공격자 목적에 쓰는 "분기 조종(Branch Steering)"은 스크린샷 검증과 DOM 검증을 모두 통과했다. 성능은 최상위 모델 성능의 최대 57%를 유지하는 수준이고, 평가는 브라우저 기반 과제에 한정되며 모바일 평가는 없다 ([arXiv 2601.09923](https://arxiv.org/html/2601.09923v2)). 도구 호출형에서는 FIDES가 Microsoft Agent Framework에 실험적 미들웨어로 들어가고 있으나(검색 요약) ([Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/agents/security)), 소비자용 화면 조작 에이전트에 구조적 방어가 출시된 사례는 찾지 못했다. Meta의 Rule of Two는 당장 쓸 수 있는 설계 규율이다. 범용 폰 에이전트는 세 조건을 거의 항상 모두 갖추므로, 이 규칙은 사람 확인이나 작업별 앱 허용목록을 요구하게 된다. 벤더가 출시한 구성과 일치한다 ([Willison, 2025-11-02](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)).

**의미 단위 행동 계층.** 업계는 구조화 인터페이스를 우선하고 GUI를 마지막 수단으로 두는 쪽으로 수렴했다. Anthropic은 커넥터, 브라우저, 화면 조작 순의 우선순위를 명시한다 ([Claude Help](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork)). Gemini 화면 자동화는 연결된 앱으로 제공되는 앱에서는 작동하지 않는다 ([Pixel Phone Help](https://support.google.com/pixelphone/answer/16940971?hl=en)). Google Play는 2027년 4월 14일부터 AppFunctions가 AI 에이전트를 속이거나 조작하지 못하도록 요구한다 ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/16585319)). 구조화 인터페이스가 인젝션을 없애는 것은 아니다. 공격이 도구 설명과 도구 출력으로 옮겨 갈 뿐이다. 그래도 참조 모니터와 출처 라벨이 붙을 대상이 생긴다는 이득이 있다. 모바일 OS는 각 창과 접근성 노드를 어느 패키지가 그렸는지 알고 있어 요소 단위 출처 추적이 기술적으로 가능하다. 라드바우드 연구진도 관찰된 모든 UI 요소의 출처 앱 추적과 접근성 트리·스크린샷 일관성 점검을 권고했다. 다만 이것은 평가되지 않은 권고이고, 같은 논문은 비전을 "신뢰할 수 있는 보안 경계가 아니라 보조 맥락"으로 보아야 한다고 경고한다 ([arXiv 2608.08939](https://arxiv.org/html/2608.08939v1)). 이 출처 정보를 모델에 보안 라벨로 노출하는 제품이나 논문은 찾지 못했으며, 이 방향은 노트 작성자의 추론이다.

**의미가 유지되는 확인.** 사람 확인은 가장 널리 출시된 최후 방어선이지만 연구는 그것이 빠르게 무뎌진다고 본다. 승인 흐름 공격을 다룬 2026년 10월 논문은 신뢰 카드 표시가 위조 설명 공격의 성공률을 0.54에서 0.03으로 낮췄다고 보고했다. 그러나 승인 폭주 공격은 여전히 0.45~0.60의 성공률을 보였고, 이 결과는 사용자 연구가 아니라 모델링된 승인자를 대상으로 한 것이다(검색 요약) ([arXiv 2610.21063](https://arxiv.org/pdf/2610.21063)). 확인 화면을 모델이 쓰지 않고 실제 실행될 행동에서 도출해 신뢰 표면에 그리자는 제안(Verifiable Action Card)과, 승인한 작업과 실행된 작업이 달라지는 공격(Loopjacking)도 같은 맥락에 있다(모두 검색 요약) ([arXiv 2609.18411](https://arxiv.org/pdf/2609.18411), [arXiv 2609.21081](https://arxiv.org/pdf/2609.21081)). Android에는 TEE가 화면을 그리고 서명된 확인을 돌려주는 Protected Confirmation이 이미 있다. 이것이 에이전트 행동 확인에 쓰인 제품 사례는 찾지 못했다 ([Android Developers](https://developer.android.com/privacy-and-security/security-android-protected-confirmation)). 사용자가 Claude Code 권한 요청의 93%를 승인한다는 수치는 2차 인용이며 원문 검증이 필요하다 ([changkun.de](https://changkun.de/blog/ideas/human-in-the-loop-agents/)).

**스크린샷 프라이버시.** 화면 에이전트는 과제와 무관한 민감 정보까지 캡처한다. 이에 대한 연구는 기기에서 요소를 식별해 선택적으로 가린 뒤 클라우드 모델에 보내는 방향이다. MaskClaw, CAPED, PriMobiBench가 그 예다. 이들은 일괄 마스킹이 에이전트에 필요한 단서를 없애므로 민감하면서 과제와 무관한 요소만 가려야 한다고 주장하지만, 모두 검색 요약 수준에서 확인했고 벤치마크도 소규모이거나 합성이다 ([arXiv 2605.28646](https://arxiv.org/pdf/2605.28646), [arXiv 2606.12666](https://arxiv.org/pdf/2606.12666)). Google은 Private AI Compute와 pKVM을 Gemini Intelligence의 데이터 보호 요소로 들지만 이를 화면 자동화가 아니라 Magic Cue 같은 주변 데이터 기능과 연결해 설명한다. 화면 자동화 스크린샷이 그 안에서만 처리되는지는 문서에 없다 ([Google, 2026-05-12](https://blog.google/security/android-gemini-intelligence-security-privacy/)). CaMeL 계열 저자들은 클라우드 모델이 화면을 보지 않고 계획하고 로컬 모델이 인식을 맡는 분할 배치를 제안한다 ([arXiv 2601.09923](https://arxiv.org/html/2601.09923v2)).

**신원, 위임, 결제.** 표준화가 가장 활발한 영역이다. IETF의 Web Bot Auth 작업반 초안은 에이전트가 HTTP 요청에 서명하게 하되, 유효한 서명이 운영자의 선의나 권한을 입증하지는 않는다고 명시한다(검색 요약) ([IETF datatracker](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol)). Visa Trusted Agent Protocol과 Mastercard Agent Pay는 그 위에 에이전트 등록과 결제 토큰을 얹는다 ([Cloudflare](https://blog.cloudflare.com/secure-agentic-commerce/)). Stripe의 Shared Payment Token은 카드번호를 노출하지 않고 사용 한도와 만료가 걸린 참조를 준다(검색 요약) ([Stripe](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens)). 모델 바깥의 주체가 강제하는 한도는 인젝션에 영향받지 않는 드문 방어다. 그러나 이 체계는 에이전트가 자기 자격증명으로 HTTP API에 접근한다고 가정한다. 사용자의 로그인된 앱에서 "결제"를 탭하는 폰 에이전트에는 서명된 위임도, 에이전트 신원도, 지출 한도도 없다. 온디바이스 에이전트가 신원 키를 어떻게 발급받고 증명하는지 다룬 자료는 찾지 못했다. AP2 등의 세부 사항은 2차 자료 간에 상충하므로 사양 원문 확인이 필요하다.

**복구, 감사, 공급망.** GUI 에이전트의 행동을 가역, 보상 가능, 비가역으로 나누고 "완전한 가역성이라는 위험한 환상"을 경고하는 연구가 있다(검색 요약) ([arXiv 2610.20100](https://arxiv.org/pdf/2610.20100)). Microsoft는 변조 방지 감사 로그를 원칙으로 선언했지만 구현 문서는 찾지 못했다 ([Microsoft Support](https://support.microsoft.com/en-us/windows/ai/ai-features/experimental-agentic-features)). 장기 실행에서는 메모리와 계획 힌트가 새 공격 표면이 된다. 오염된 앱별 안내 카드(AppCard)는 접근성 트리를 거치지 않고 계획 단계에 주입되어 공격 성공률 1.0을 기록했다 ([arXiv 2608.08939](https://arxiv.org/html/2608.08939v1)). 스킬 마켓플레이스에서는 2026년 2~5월 사이 악성 스킬 1,184개 이상이 확인되었다는 보고가 있으나 CSA 노트를 통한 검색 요약이며 원 연구는 읽지 못했다 ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-skill-supply-chain-attacks-20260624-csa/)).

## 앱의 동의를 묻는 중국, 아직 초안인 한국

화면 조작은 조작당하는 앱의 동의 문제를 낳는다. 중국은 이를 가장 먼저 겪었다. 2025년 12월 출시된 도우바오 폰은 시스템 권한으로 화면을 읽고 탭했고 단계마다 스크린샷을 클라우드로 올렸다. 며칠 만에 위챗, 타오바오, 알리페이와 여러 은행 앱이 차단하거나 제한했다. 은행은 에이전트의 행동과 사용자의 행동을 구분할 수 없었다 ([Lawfare, 2026-03-06](https://www.lawfaremedia.org/article/china-s-agentic-ai-controversy)). 에이전트에 필요한 권한(화면 읽기, 입력 주입, 오버레이)이 은행 악성코드가 악용해 온 권한과 겹치기 때문에, 앱 쪽 이상 거래 탐지가 에이전트를 사기로 분류한 것이다. 이후 규범이 뒤따랐다. 2026년 9월 보도된 금융 분야 단체표준은 제3자 온디바이스 에이전트가 "금융기관의 수권 없이 시스템 권한으로 금융 앱 GUI를 자동으로 읽거나 조작해서는 안 된다"고 규정하며, 업계는 이를 사용자와 기관의 "이중 수권"이라 부른다. 조항과 표준 번호는 신문 보도 한 건에 근거하며 원문은 확보하지 못했다 ([封面新闻, 2026-09-11](https://cbgc.scol.com.cn/news/7944927)). 2세대 도우바오 폰은 36Kr 보도에 따르면 "프로토콜 우선, 시뮬레이션 보조, 사람 확인"으로 전환했다. 앱이 페이지와 조작 유형별 경계를 선언하는 SAEP 규약 아래 로그인·결제 화면은 조작 대상에서 제외된다 ([36Kr, 2026-09](https://eu.36kr.com/zh/p/3986222650283657)). 다만 다른 보도는 화면 읽기와 모의 클릭을 아예 중단했다고 전해 강조점이 엇갈린다. 150여 개 앱이 거부했다는 수치와 공업정보화부의 11월 통지 내용은 검색 요약으로만 확인했다 ([Xinhua, 2026-11-06](https://www.news.cn/20261106/b56a8a3cb14e40a69d997b37b39cc99a/c.html)).

Android는 반대 구조다. Computer Control 문서는 대상 앱이 통합을 위해 "추가 변경을 할 필요가 없다"고 쓰고, 앱 측 거부 수단은 문서화하지 않는다 ([Android Developers](https://developer.android.com/ai/computer-control)). 앱 개발자가 쓸 수 있는 수단은 기존의 `FLAG_SECURE`, `accessibilityDataSensitive`, Play Integrity 정도다. 이들이 Computer Control의 가상 디스플레이에서 어떻게 동작하는지에 대한 자료는 찾지 못했고, 이 세 가지는 이번 조사에서 재확인하지 않은 배경 지식이다. 미국에서는 제9순회항소법원이 2026년 8월 Amazon 대 Perplexity 사건의 가처분을 취소했다. 법원은 에이전트를 "사용자의 지시에 따라 움직이는 도구"로 보면서도 이 판단이 에이전트형 AI의 일반 법리를 세우는 것은 아니라고 한정했다. 판결문 자체는 확보하지 못했고 업계 매체 보도에 근거한다 ([Retail Insight Network](https://www.retail-insight-network.com/newsletters/us-court-overturns-amazon-injunction-perplexity)). 인젝션으로 발생한 결제의 책임은 어느 관할에서도 정리되지 않았으며, 벤더와 가맹점 약관은 책임을 사용자에게 둔다.

한국의 제도는 준비 단계다. 개인정보보호위원회는 2026년 9월 23일 에이전틱 AI를 주제로 민관 정책협의회를 열었다. 15개 기업 조사에서는 프롬프트 인젝션과 과도한 권한이 주요 위험으로 꼽혔다. 위원회는 에이전트가 단독으로 할 수 있는 일과 사람 승인이 필요한 일의 구분, 책임 배분, 로그·메모리의 보존과 삭제를 쟁점으로 삼아 가칭 "에이전틱 AI 개인정보 처리 안내서"를 2026년 말까지 마련할 계획이다 ([MTN, 2026-09-23](https://news.mtn.co.kr/news-detail/2026092316363993251)). 금융보안원은 10월 7일 AI 에이전트 보안 평가기준(안)을 발표했다. 실행 권한과 격리, 도구 실행과 승인 통제, 작업 범위와 결과 검증, 자율 실행 제한과 중단 가능성을 포함한 17개 항목을 연말까지 시범 검증한다 ([파이낸셜뉴스, 2026-10-07](https://www.fnnews.com/news/202610071821048238)). AI 기본법은 2026년 1월 22일 시행되었으나, AI가 직접 행동해 사고가 났을 때 책임을 배분하고 구제하는 절차가 부족하다는 비판이 11월 보도에 있다(검색 요약) ([ZDNet Korea, 2026-11-16](https://zdnet.co.kr/view/?no=20261116162921)). KISA나 과학기술정보통신부의 에이전트 전용 문서, 전자금융거래법을 에이전트가 수행한 거래에 적용한 금융당국의 입장, 중국식 이중 수권에 해당하는 규칙은 찾지 못했다. 다만 검색 범위가 제한적이어서 부재가 확인된 것은 아니다. 국제 프레임워크(OWASP 에이전트 Top 10, NIST CAISI 이니셔티브, MITRE ATLAS)는 화면 조작을 "도구를 가진 에이전트"의 한 사례로만 다루고 화면 고유의 위험을 직접 규정하지 않는다(검색 요약) ([Pillsbury](https://www.pillsburylaw.com/en/news-and-insights/nist-ai-agent-standards.html)).

## 결론

화면 조작 에이전트의 보안 수준은 화면 조작을 얼마나 줄였느냐에 좌우된다. 격리, 허용목록, 결제 직전 사람 인계라는 현재 구성은 사실상 Rule of Two를 제품으로 구현한 것이다. 연구 중인 구조적 방어, 위임 프로토콜, 신뢰 확인은 모두 타입 있는 행동과 식별 가능한 주체를 전제한다. 따라서 인증과 결제 같은 고위험 단계는 구조화된 서명 채널로 옮겨 가고, GUI 조작은 구조화 인터페이스를 제공하지 않는 앱을 위한 대체 수단으로 남을 가능성이 크다. 보증이 가장 약하고 상대 앱의 협조가 가장 적은 곳이 바로 그 영역이다. 허용된 앱 안에서 공격자가 쓴 콘텐츠가 정상 분기를 악용하는 데이터 흐름 문제에는 아직 알려진 해법이 없다.

한국의 갤럭시 사용자와 서비스 사업자에게 당장 의미 있는 질문은 세 가지다. 국내 금융·메신저 앱이 Gemini의 허용목록에 들어가는지와 그 결정에 앱 사업자가 관여할 수 있는지, 삼성과 Android의 활동 기록이 분쟁 시 증거가 될 만큼 변조 방지와 내보내기를 갖추는지, 연말에 나올 개인정보보호위원회 안내서와 금융보안원 기준이 "사용자 동의면 충분하다"와 "앱의 동의도 필요하다" 가운데 어느 쪽을 택하는지다. 이 세 가지 모두 현재 공개 자료로는 답할 수 없다. 출시된 폰 에이전트를 보호 장치가 켜진 상태에서 적응형 공격으로 평가한 독립 측정이 나오기 전까지는, 화면 자동화를 은행·의료·공공 앱 밖에 두라는 벤더의 권고를 따르는 것이 합리적인 기준이다.
