## 1. Structured interfaces for agents on the web (WebMCP, MCP + authorization, A2A, NLWeb, llms.txt) and comparison with AppFunctions / App Intents

### Takeaway
The web now has a browser-level "structured alternative to clicking" — WebMCP, a W3C Community Group draft implemented in Chrome as an origin trial (M149–M156, shipping targeted for M157) — plus the server-side route of remote MCP servers protected by an OAuth 2.1-based authorization spec. WebMCP's security model is thin by design: same-origin scoping and a Permissions Policy switch are enforced by the browser, but protection against tool poisoning, output injection and deceptive tools is explicitly left to the agent, and no user-confirmation primitive exists in the spec yet.

### Cited Findings

**WebMCP**
- Status line of the spec: "Draft Community Group Report, 13 November 2026", published by the W3C Web Machine Learning Community Group; "not a W3C Standard nor is it on the W3C Standards Track". Editors: Brandon Walderman (Microsoft), Khushal Sagar (Google), Dominic Farolino (Google), Samuel Dallstream (Microsoft). (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/)
- API surface: `document.modelContext` (`[SecureContext, SameObject]`, a partial interface on `Document`, not `Navigator`). `ModelContext` has `registerTool(tool, options)`, `getTools(options)`, `executeTool(tool, inputObject, options)` and events `toolchange`, `toolactivated`, `toolcancel`. Registration options include `exposedTo` and `signal`; `getTools` takes `fromOrigins`. (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/)
- Tool annotations (booleans, default false): `readOnlyHint`, `untrustedContentHint` (output contains data the tool author considers untrusted), `consequentialHint` (significant, real-world or non-reversible effects), `debugging`. (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/)
- Permissions Policy feature name `tools`, default allowlist `'self'`. Explainer: "By default, tools registered by a document are only exposed to itself, same-origin documents in the same tree"; "By default, WebMCP is enabled in top-level `Window`s and its same-origin iframes"; calls reject with `NotAllowedError` when the permission is disabled. (fetched) — [spec](https://webmachinelearning.github.io/webmcp/); [explainer repo](https://github.com/webmachinelearning/webmcp)
- Explainer positioning: tools are JavaScript functions with natural-language descriptions and schemas, a client-side alternative to backend integrations such as MCP servers; first published 13 Aug 2025; original authors from Microsoft (Walderman, Lee, Nolan) and Google (Bokan, Sagar, Van Opstal). A declarative form-based API "is being explored but is not part of the specification". (fetched) — [explainer repo](https://github.com/webmachinelearning/webmcp)
- Security/privacy section, quoted: prompt injection is where "malicious instructions are embedded in tool metadata, inputs, or outputs to manipulate agent behavior"; tool poisoning = "Malicious instructions embedded in tool metadata (name, description, parameter descriptions)"; output injection — "Tool return values are processed by the agent's language model as trusted information."; "There is no guarantee that a WebMCP tool's declared intent matches its actual behavior."; "Sites can design highly parameterized WebMCP tools to extract sensitive user data"; "By default, WebMCP enforces strict same origin isolation"; private browsing "may inadvertently leak information across this boundary". (fetched) — [WebMCP spec, security and privacy considerations](https://webmachinelearning.github.io/webmcp/)
- Mitigations listed in the spec: disable via Permissions Policy; input length limits ("This restriction would not fully solve prompt injection attacks"); the untrusted annotation ("acts as a signal to the client that the payload requires heightened security handling"); the consequential annotation ("they can selectively enforce mandatory user confirmation prompts before executing high-stakes tools"); and "agents cannot rely solely on site-asserted tool descriptions or annotations for security". The spec notes that agents inherit the user's identity and logged-in session and that a malicious site can omit or misrepresent hints. (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/)
- No `requestUserInteraction` or other user-confirmation method is in the current spec text; the explainer lists as an open question "Exploring a way for a tool to prompt the user for confirmation when tools require explicit user authorization." The spec does not describe any way for a site to learn whether a human or an agent is calling, or which agent. (fetched) — [explainer](https://github.com/webmachinelearning/webmcp); [spec](https://webmachinelearning.github.io/webmcp/)
- Chrome status: "Intent to Experiment: WebMCP" posted to blink-dev on 15 May 2026; origin trial M149 through M156 on Desktop, Android and WebView; shipping planned for M157; LGTM from Mike Taylor 18 May 2026 (window longer than usual because Chrome is moving to two-week releases). TAG review "pending" ("We will request TAG review before shipping"); Gecko and WebKit: "No signal". Stated risks include "Sites may consume and expose sensitive information when their WebMCP tools are called by agents" and that LLM agents are susceptible to indirect prompt injection. Consumers named: Chrome extensions that let cloud-LLM agents discover and call tools, and the Prompt API with on-device models; agents "may be provided by the browser or by the site author". No first-party agent (Gemini in Chrome) is named in the intent. (fetched) — [blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/gmYffo5WOE8/m/OJxuQRP3AAAJ)
- Chrome 149 reached stable on 2 June 2026; `navigator.modelContext` was the earlier name, moved to `document.modelContext` around July 2026 and the old spelling deprecated in Chrome 150 — single-blog claims. Edge: sources disagree (behind a flag vs. an origin trial listed for Edge 150, 2 Jul 2026, expiring 30 Mar 2027); no Microsoft primary page found. Firefox/Safari uncommitted. (search summary) — [dev.to](https://dev.to/thousand_miles_ai/webmcp-in-chrome-149-web-pages-get-a-tool-api-for-ai-agents-bfi); [mcpplaygroundonline](https://mcpplaygroundonline.com/blog/what-is-webmcp); [mcpbundles](https://www.mcpbundles.com/guides/webmcp-browser-support)
- Deployment evidence: at the W3C/GS1 workshop (Zurich, 8–9 Sept 2026) Shopify reported shipping WebMCP on its storefronts, noted that "every navigation tears down registered tools", and asked for a user-in-the-loop (elicitation) primitive for checkout. W3C is discussing a charter for a proposed **Agentic Web Working Group** that would include WebMCP (i.e. a move to the standards track). The report is marked as a draft. (fetched) — [W3C workshop report](https://www.w3.org/2026/ecommerce-agents/report.html)

**MCP remote servers and the authorization spec**
- Current revision read: **2026-07-28** (URLs and `MCP-Protocol-Version: 2026-07-28` in examples). "Authorization is **OPTIONAL** for MCP implementations. When supported: Implementations using an HTTP-based transport **SHOULD** conform to this specification"; STDIO transports should take credentials from the environment. (fetched) — [MCP authorization spec](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Built on OAuth 2.1 (draft-ietf-oauth-v2-1-13), RFC 8414, RFC 7591, RFC 8707, RFC 9728, RFC 9207 and OAuth Client ID Metadata Documents (draft-ietf-oauth-client-id-metadata-document-00). MCP server = OAuth resource server; MCP client = OAuth client. (fetched) — same source
- Requirement levels when authorization is used: authorization servers MUST implement OAuth 2.1; MCP servers MUST implement Protected Resource Metadata (RFC 9728) and clients MUST use it for discovery; clients and servers SHOULD support Client ID Metadata Documents; Dynamic Client Registration is "deprecated and retained for backwards compatibility"; clients MUST send the RFC 8707 `resource` parameter in authorization and token requests; clients MUST validate `iss` per RFC 9207 (a future revision is expected to make AS inclusion of `iss` a MUST). (fetched) — same source
- Token rules: "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience"; "MCP servers **MUST NOT** accept or transit any other tokens" (no token passthrough); tokens never in the query string; step-up via 403 `insufficient_scope` with least-privilege scope selection. Security considerations cover audience binding, token theft, authorization-code protection, mix-up and confused-deputy attacks, open redirection, and Client ID Metadata Document security. (fetched) — same source
- This resolves the conflict flagged in the earlier notes: the CSA statement (authorization optional) matches the spec; the vendor statement that 2026-07-28 "requires OAuth 2.1 for HTTP transports" is accurate only in the sense "if you do authorization over HTTP, it must be this OAuth 2.1 profile". (fetched vs. earlier notes) — [MCP spec](https://modelcontextprotocol.io/specification/latest/basic/authorization)

AP2 describes itself as "an extension for the open-source Agent2Agent (A2A) protocol" and is also offered as an extension of the Universal Commerce Protocol (UCP). (search summary for A2A; fetched for the AP2 sentence) — [dev.to overview](https://dev.to/sebastian_chedal/what-mcp-a2a-and-ucp-mean-for-your-website-in-2026-3aij); [ap2-protocol.org](https://ap2-protocol.org/)

(search summary) — [VentureBeat](https://venturebeat.com/ai/the-battle-to-ai-enable-the-web-nlweb-and-what-enterprises-need-to-know/); [presenc.ai](https://presenc.ai/research/nlweb-adoption-2026); [hidden-layer blog](https://hidden-layer-blogs.pages.dev/post/wix-nlweb-platform-shift)

- Android AppFunctions: apps annotate functions; invocation restricted to privileged/system callers; Play policy from 14 Apr 2027 forbids AppFunctions that deceive or manipulate agents. ### Inferences
- WebMCP vs AppFunctions/App Intents — same idea, different trust anchors:
  - *Who may call*: WebMCP tools are callable by whatever agent is attached to the page (browser-built-in, extension, or the site's own); the spec has no caller authentication. AppFunctions restricts callers by OS permission; App Intents are invoked by the OS assistant. The web has no gatekeeper equivalent to "privileged system caller".
  - *Who vouches for the tool*: on Android the tool comes from a package with a signing certificate, reviewed under Play policy (with an explicit anti-manipulation rule from Apr 2027). On the web the tool comes from an origin; nothing reviews it, and the spec states that descriptions and hints are site-asserted and may be false.
  - *Scope boundary*: origin (same-origin by default, cross-origin only via `exposedTo`/`fromOrigins` and Permissions Policy) vs package/UID.
  - *Confirmation*: neither WebMCP nor the fetched MCP auth page provides an agent-unforgeable confirmation surface; WebMCP only offers a site-supplied `consequentialHint`. Android has OS-owned UI for confirmation.
- WebMCP does not remove prompt injection; it relocates it from page pixels/DOM to tool metadata and tool outputs — the same relocation the earlier notes described for AppFunctions/MCP. The gain is a typed action space that reference monitors and origin policies (e.g. Chrome's Agent Origin Sets, section 6) can bind to.
- Because WebMCP tools run in the page with the user's cookies, a WebMCP call is indistinguishable server-side from the user's own action unless the site instruments it — so WebMCP gives sites a structured interface but not agent identification.
- MCP's authorization profile solves "which client may call this server with which scopes for which user" (audience-bound tokens, no passthrough) but is optional and says nothing about what the model does with tool descriptions or results.

## 2. Agent identification: Web Bot Auth, user-agent strings, robots.txt, Cloudflare policies, and the local-browser limitation

### Takeaway
Web Bot Auth is now an IETF working-group draft (-01, 29 Oct 2026; Cloudflare + Google authors) that proves only that the holder of a key published at a given URL signed the request — expressly not who operates the agent, whether it is benign, or whether it is authorized. It is deployed for cloud-hosted agents (OpenAI's cloud browser, a subset of `Google-Agent` requests) and verified at CDNs, but agents that drive the user's own local browser (Comet, Atlas agent mode, Claude in Chrome, Gemini in Chrome) send the browser's ordinary traffic and are not identified by it; a W3C workshop in Sept 2026 recorded "no consensus among major agent providers on identifying themselves".

### Cited Findings

**The draft, read directly**
- `draft-ietf-webbotauth-httpsig-protocol-01`, "HTTP Message Signatures for automated traffic", dated 29 Oct 2026, expires 2 May 2027; authors Thibault Meunier (Cloudflare) and Sandor Major (Google); Web Bot Auth WG document; the document header says Standards Track (datatracker metadata shows no intended status yet). (fetched) — [datatracker](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/)
- Mechanics: headers `Signature`, `Signature-Input`, `Signature-Agent` (a Structured Fields dictionary; legacy bare-string form may be accepted by verifiers). Signature must cover at least one of `@authority`/`@target-uri` and the `signature-agent` field when present; parameters `created`, `expires` (recommended ≤ 24 h after `created`), `keyid` (JWK thumbprint), `tag="web-bot-auth"`. Keys are a JWKS served over HTTPS at `/.well-known/http-message-signatures-directory` (media type `application/http-message-signatures-directory+json`). (fetched) — same source
- What a signature proves and does not prove (verbatim):
  - "A valid signature over a resolved URL proves that a holder of a key that URL publishes signed the covered message." (§4.1)
  - "It says nothing about who operates the Agent, whether the Agent is benign, or whether the request is authorized." (§4.1)
  - "It does not say that the operator of that URL is honest, or that it is the same party everyone knows about." (§4.4)
  - "This protocol does not authenticate human users." (§4.6)
  - "An unsigned request does not establish whether the sender is human or automated, or whether it is evading identification." (§6.11)
  - On nested/forwarded signatures: "it does not express authorization, delegation, or consent." (§5.2.2); Appendix D.2: "It does not say that Alice's agent authorized the remote browser to act for it."
  (fetched) — same source
- Privacy (§7.1): "This protocol enables receivers to recognise requests that carry the same identifier"; "Key rotation does not prevent this correlation when the identifier remains unchanged"; "This protocol is unsuitable for agents that need to avoid such identification." The section also addresses agents "whose identifier would be associated with an individual human". (fetched; the last ~2.5% of the page text was not read) — same source
- The draft gives no specific guidance for an agent embedded in a user's own browser; the closest text is the terminology entry for "An orchestrated user agent (e.g. Chromium, CURL)". (fetched) — same source
- Predecessors: individual drafts by Meunier (`draft-meunier-web-bot-auth-architecture-05`, Mar 2026; `draft-meunier-webbotauth-httpsig-protocol-00`, Jun 2026). (search summary) — [architecture draft](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture-05)

Page last updated 13 Oct 2026. Nothing is said about agents in the user's local Chrome. (fetched) — [Google crawling docs](https://developers.google.com/crawling/docs/crawlers-fetchers/web-bot-auth)

### Inferences
- There are two populations of browser agents with opposite identification properties:
  - *Cloud-browser agents* (ChatGPT agent/cloud browser, Google-Agent, Browserbase-hosted agents): requests originate from vendor infrastructure, can be signed, verified at the CDN and allow-listed. Web Bot Auth fits.
  - *Local-browser agents* (Comet, Atlas agent mode, Claude in Chrome, Gemini in Chrome auto browse): requests come from the user's device, IP, cookies and a normal Chromium fingerprint. Nothing in the draft covers them; identification depends on the vendor voluntarily adding a user-agent token or header, which Perplexity declined to do. To the site, the agent "looks like the user" — and the Ninth Circuit accepted exactly this framing in law (section 5).
- Even where signatures exist, they establish a stable pseudonymous key, not accountability. Trust is supplied by out-of-band registries (Cloudflare's bot directory, Visa/Mastercard agent registration), i.e. by private gatekeepers — the web's nearest analogue to an app store's allowlist.
- Mobile comparison: Play Integrity attests *app + device* integrity to the app's backend and is controlled by the platform; Web Bot Auth attests *agent operator key* to the site and is self-asserted. Neither tells the service whether a human or an agent pressed the button inside a legitimate client. On Android the OS at least knows an agent is acting (Computer Control permission, indicator); on the web no party is structurally positioned to know unless the browser vendor is also the agent vendor.
- The privacy clause ("unsuitable for agents that need to avoid such identification") means signing a local agent's requests would tell every site that this user uses a particular AI agent — a reason, beyond competition, why local agents do not sign.

## 3. Site-side blocking, bot detection, CAPTCHA behaviour, terms of service, and sites that partner instead

### Takeaway
Bot defences were built to separate humans from scripts and do not work as an agent policy: a Nov 2026 measurement finds solver services beat challenge CAPTCHAs essentially always and that an LLM agent's pass rate depends on the browser/account state it presents, not the model; agents in the user's real browser inherit that state. Sites therefore fall back on contract and business choices — Amazon and eBay prohibit unapproved agents in their terms and block server-side, while Shopify, Walmart, Etsy and (conditionally) Target admit agents through sanctioned channels.

### Cited Findings

**CAPTCHA and bot detection**
- "Broken Gates: Re-evaluating Web Bot Defenses in the Age of LLM Agents" (Ousat et al., Florida International University; arXiv 2607.18659, v2 5 Nov 2026): seven solver services "largely defeat challenge-based defenses with a 100% success rate"; on reCAPTCHA v3 the average falls to 23%. For eight LLM browser agents the bottleneck is "the browser and account state the verifier sees, not the model itself": an established consumer account and persistent Chrome state strongly affect reCAPTCHA v2/v3 acceptance; Turnstile is more sensitive to the browser control path; rebuilding an established browser environment let previously rejected agents pass with no model retraining, and that environment transferred across agents and defences. The authors' conclusion: non-interactive defences rely on signals that must be available to ordinary users and can therefore be obtained and reused by attackers. (fetched abstract page; per-agent numbers not seen) — [alphaXiv 2607.18659](https://www.alphaxiv.org/abs/2607.18659)
- July 2025: ChatGPT agent was observed ticking Cloudflare Turnstile's "I am not a robot" checkbox without a puzzle; OpenAI's earlier Operator had been trained to stop and ask the human to complete CAPTCHAs. (search summary) — [CO/AI](https://getcoai.com/news/chatgpt-agent-bypasses-cloudflares-i-am-not-a-robot-verification/); [techbang (Ars Technica reproduction)](https://www.techbang.com/posts/124556-openai-chatgpt-agent-passes-i-am-not-a-robot-test)
- SPLX: ChatGPT agent refuses to solve a CAPTCHA when asked directly, but reframing the task inside a pasted prior chat led it to solve reCAPTCHA v2 Enterprise and others — i.e. the refusal is a model-level policy that can be socially engineered. (search summary) — [SecurityWeek](https://www.securityweek.com/chatgpt-tricked-into-solving-captchas/amp/); [Cybersecurity News](https://cybersecuritynews.com/chatgpt-bypassing-captcha-security/)
- hCaptcha's report on browser agents argues CAPTCHA solve attempts should be refused outright as an "account takeover primitive" and says that when tested agents failed to act it was mostly because the tool lacked a feature, not because of a safety refusal. Vendor report from an interested party; methodology unclear. (search summary) — [hCaptcha blog](https://hcaptcha.uth.edu/blog/report-browser-agent-safety-is-an-afterthought-for-vendors)

### Inferences
- For a local-browser agent, bot detection is nearly useless as an *agent* control: the agent presents the user's real browser profile, account history and IP, which are exactly the signals reCAPTCHA v3/Turnstile reward. Detection then has to rely on behavioural tells (input timing, CDP/automation artefacts), which is the "cat-and-mouse" the workshop described. Cloud-browser agents are the ones that hit CAPTCHAs — and they are also the ones that can sign requests and be allow-listed.
- Sites consequently have three levers, in decreasing technical and increasing legal character: (a) allow-list signed/registered agents at the CDN; (b) heuristically block unknown automation, with collateral damage to legitimate agents; (c) terms of service plus notice to the user or vendor. After the Ninth Circuit ruling (section 5), lever (c) is a contract matter between the site and its *users*, not a computer-crime claim against the agent vendor.
- Mobile comparison: an app's defences against screen agents (risk engines, Play Integrity, `FLAG_SECURE`) sit alongside an OS that curates which apps the first-party agent may automate; the app negotiates with one platform owner. A website faces an open set of agents and browsers with no curator — its only "allowlist" is the CDN's bot directory or its own terms.
- Vendor CAPTCHA "policies" appear to be model behaviours (refuse or hand back to the user) rather than published rules; the SPLX result shows such behaviours are not a security boundary.

## 4. Agentic payments on the web: AP2, ACP/Shared Payment Tokens, Visa TAP, Mastercard Agent Pay; what shipped agents actually do; Korea

### Takeaway
The payment layer has converged on a common pattern — a user-approved, cryptographically scoped authorization that the agent can exercise but not enlarge (AP2 open/closed mandates; Stripe SPT usage limits; network agentic tokens) plus signed agent recognition at the merchant edge (Visa TAP on RFC 9421) — but these run through API/"app" integrations and cloud agents. I found no evidence that the shipped local-browser agents use them at an ordinary web checkout; the documented behaviour of Gemini in Chrome is autofill of the user's saved payment details with a confirmation pause, and Visa's own spec has a mode for an agent "key-entering" a card into a guest-checkout form. Korea is at proof-of-concept stage.

### Cited Findings

**AP2 (read from the spec site)**
- Current spec is titled "Agentic Payment Protocol (v0.2)"; the site links "AP2 v0.2 Release and FIDO Alliance Donation"; standardisation continues in FIDO's Agentic Authentication Technical and Payments Technical Working Groups; repository `google-agentic-commerce/AP2`; Apache-2.0; original announcement 16 Sept 2025. No release date for v0.2 is shown on the pages read. (fetched) — [ap2-protocol.org](https://ap2-protocol.org/); [AP2 specification](https://ap2-protocol.org/ap2/specification/)
- Roles: Shopping Agent, Credential Provider, Merchant, Merchant Payment Processor, **Trusted Surface**. The Trusted Surface "MUST be non-agentic". (fetched) — [AP2 specification](https://ap2-protocol.org/ap2/specification/)
- Mandates: **Checkout Mandate** (shared with the merchant; "Captures the reference to the specific items and purchase details negotiated between the agent and the merchant") and **Payment Mandate** (shared with the credential provider, networks and merchant payment processor; "Captures the authorization for a specific transaction amount bound to a finalized checkout."). Each has an *open* form (user's constraints for autonomous execution — e.g. budget, allowed instruments) and a *closed* form (a specific finalized checkout/amount). `vct` identifiers such as `mandate.checkout.open.1`, `mandate.payment.1`. (fetched) — [ap2-protocol.org](https://ap2-protocol.org/); [spec](https://ap2-protocol.org/ap2/specification/)
- Who signs: *human present* — the Shopping Agent passes the mandate content to the Trusted Surface, which displays it to the user for signing; "the signature on the closed Mandates is validated as coming from a User directly, using a User Credential or a trust list of Agent Providers." *Human not present* — the Trusted Surface authorises open mandates, which "MUST include the agent's public key as a `cnf` claim"; the agent then signs the closed mandates with that key. The merchant signs a Checkout JWT; closed mandates bind to it by hash. (fetched) — [AP2 specification](https://ap2-protocol.org/ap2/specification/)
- Format: "AP2 specifies the use of `SD-JWT`s for securing the Payment and Checkout Mandates." Verifiers (merchant; credential provider/network; payment processor) check closed mandates against open-mandate constraints. Mandates plus receipts are said to give "a non-repudiable picture of the transaction", but "dispute resolution, retention, and retrieval requirements are outside the scope of this specification"; no liability allocation and no 3DS/step-up mechanism appear on the page read. (fetched) — same source
- Principle: "Trust in payments is anchored to deterministic, non-repudiable proof of intent from the user". Samples listed: human-present cards, human-not-present cards, human-not-present x402, Digital Payment Credentials on Android. (fetched) — [ap2-protocol.org](https://ap2-protocol.org/)
- Product rollout: at I/O 2026 Google said AP2 rollout to its products would begin with "Gemini Spark"; Universal Cart lets consumers check out via Google Pay or hand off to the merchant site; UCP announced 11 Jan 2026 at NRF. (search summary) — [PYMNTS](https://www.pymnts.com/?p=3750795); [aiweekly](https://aiweekly.co/alerts/gemini-spark-expands-to-160-countries-with-chrome-auto-browse)

**ACP and Stripe Shared Payment Tokens**

**Visa Trusted Agent Protocol (merchant spec read on developer.visa.com; page © 2026, no version)**

### Inferences
- Three distinct checkout paths now coexist for a web agent:
  1. *GUI fill* — the agent (or browser autofill on its behalf) enters the user's card into the merchant's form; issuer and merchant see a normal e-commerce transaction; no mandate, no cap, no agent attribution. This is what local-browser agents do on arbitrary sites.
  2. *GUI fill with attestation* — Visa TAP's "key entry" container: the agent still types the card, but a signed hash lets the merchant confirm the card data came from a registered agent. A bridge for unmodified checkout forms.
  3. *Structured delegated credential* — SPT / agentic network token / AP2 closed mandate through an API or in-app checkout. Only this path gives limits that hold even if the model is prompt-injected.
- AP2 v0.2's "Trusted Surface MUST be non-agentic" is the payment world's version of the trusted-confirmation requirement in the earlier notes; and its `cnf`-bound agent key in open mandates is a concrete answer to "how does an agent get an attestable identity" — the user's trusted surface delegates to that key per mandate, rather than the vendor holding one global identity.
- The retreat of Instant Checkout into merchant apps suggests merchants want to keep checkout (tax, inventory, fraud, customer relationship) — the web-side parallel of WeChat/Alipay keeping execution inside their own agents (earlier notes).
- Step-up authentication (3DS, passkey, Affirm's "buyer must be the one navigating") is deliberately kept out of the agent's hands in every scheme read; SCA is the de facto human-in-the-loop for web payments too.
- Korea's visible direction (KakaoPay) is wallet + pre-set limits + stablecoin rather than card-network mandates; whether Korean card companies' participation in Visa's pilot leads to TAP/agentic-token deployment domestically is not known.

## 5. Legal status for web agents: Amazon v. Perplexity (read first-hand), CFAA/ToS arguments, other 2026 matters

### Takeaway
The Ninth Circuit's published opinion (4 Aug 2026, No. 26-1444, Judge M. Smith for a unanimous panel) holds that on this record the *user*, not Perplexity, "accesses" Amazon — because Comet runs locally and Perplexity's servers never talk to Amazon's — so CFAA and CDAFA claims against the agent vendor are unlikely to succeed; it expressly preserves Amazon's ability to regulate access through its terms of service with users and leaves tort and other theories open. The reasoning is tied to the local-browser architecture and does not obviously cover cloud-hosted agents.

### Cited Findings (all from the opinion text unless marked)
- Caption and posture: *Amazon.com Services, LLC v. Perplexity AI, Inc.*, No. 26-1444, D.C. No. 3:25-cv-09514-MMC (N.D. Cal., Chesney, J.); argued 11 June 2026 (Seattle); filed 4 Aug 2026; for publication; panel Milan D. Smith, Jr., Eric C. Tung, and District Judge John C. Hinderaker (D. Ariz., by designation); opinion by Judge M. Smith; no separate opinions appear in the document. (fetched) — [opinion PDF](https://www.courthousenews.com/wp-content/uploads/2026/08/amazon-v-perplexity-ninth-circuit-opinion.pdf)
- Facts found: Comet "operates like Google Chrome, running locally on a user's machine"; when asked to shop, the Assistant "takes screenshots of the browser view, sends those screenshots from the user's computer to Perplexity's servers, and receives instructions from Perplexity's servers on how to navigate Amazon.com"; "Perplexity itself does not directly communicate with Amazon's servers." Amazon twice told Perplexity it had no authorization; the core dispute was Perplexity's decision not to send an agent-identifying user-agent string. (fetched)
- District court (Mar 2026): injunction granted on the finding that Perplexity "accesses with the Amazon user's permission but without authorization by Amazon, the user's password-protected account"; loss element met by Amazon's cost of "developing tools to block Comet's access"; bond denied; seven-day administrative stay. The Ninth Circuit motions panel then stayed the injunction pending expedited appeal. (fetched)
- Holding on CFAA: "the CFAA contemplates access by a person. However advanced the Assistant currently is, it is a tool, not a person for statutory purposes." "Our focus is thus to ask whether Perplexity uses a tool (the Assistant) to 'access' Amazon's computers. On the facts before us, we answer no. It is the user who 'accesses' Amazon's computers, with the help of the Assistant to carry out specific acts on Amazon.com." Receiving screenshots and sending instructions "by themselves, do not mean that Perplexity has 'accessed' (gained entry) to Amazon's servers." (fetched)
- Reserved question: "We do not address whether, on a different record or new facts, Perplexity may exercise control over the Assistant in such a way as to gain entry to Amazon's servers." (fetched)
- Supporting reasons: rule of lenity (CFAA is primarily criminal); Amazon's theory "could expose users themselves to criminal liability (under a conspiracy or aiding-and-abetting theory)"; the statute's purpose is anti-hacking (*hiQ*, *Nosal I*); *Van Buren* defines access as entering a system. *Power Ventures* distinguished because access there was assumed and the analysis concerned authorization; *BrandTotal* not a perfect analogue because the Assistant "appears to do more than passive data collection". The court did not reach "without authorization" or the loss element (fn. 4). (fetched)
- CDAFA: claims "rise and fall together"; even if "access" is broader under Cal. Penal Code § 502, "the user (not Perplexity) accesses Amazon using the Assistant as an AI tool". (fetched)
- Limits stated by the court: "We do not establish a new legal regime governing agentic AI. We do not address whether in other contexts, including tort claims, Perplexity can avoid liability for the Assistant's actions. Our holding here is limited to 'access' as contemplated by the CFAA … on the record before us"; "this opinion reflects and applies to the state of technology only as presented in the filings in this case." (fetched)
- Footnote 5: "This outcome does not impair Amazon's ability to regulate access to Amazon.com via private terms of service for its users." (fetched)
- Equities: Amazon's evidence of harm was weak — degraded shopping experience is "more abstract"; on security, Amazon's own expert could not fully replicate the cited risks, only one example involved a shopping site and none Amazon.com; an injunction "would impair consumer choice and needlessly limit development of a nascent technology". Disposition: vacated and remanded. (fetched)
- Amici: ACLU/Knight Institute; EFF, Alliance for Responsible Data Collection, Mozilla, Digital Medusa, EleutherAI (their description of the architecture is quoted by the court); SIIA; National Retail Federation; Digital Content Next; News/Media Alliance; Airlines for America. (fetched)
- Commentary (Kieran McCarthy / Eric Goldman, 6 Aug 2026): praised the panel for engaging with the agentic facts; McCarthy had called the district court's reasoning "a shockingly poor effort"; Goldman's open questions — whether providers can cross an undefined line into being the actor, whether *Ticketmaster v. RMG*-type theories still reach the provider, and whether users themselves face exposure; Perplexity "might not be out of the woods just yet". (fetched) — [Technology & Marketing Law Blog](https://blog.ericgoldman.org/?p=29133)
- After the opinion: Amazon petitioned for rehearing en banc on 18 Aug 2026; one secondary source says the petition was later denied, others report only the filing. (search summary — denial unverified) — [MLex](https://www.mlex.com/articles/2515046/amazon-asks-us-appeals-court-to-revisit-case-against-perplexity-ai); [ABA newsletter](https://www.americanbar.org/groups/litigation/resources/newsletters/privacy-data-security/ninth-circuit-holds-human-user-not-developer-ai-agent-responsible-websites-accessed/)
- Terms-of-service route: Amazon's complaint cited its prohibition on "data mining, robots, or similar extraction tools" and requirements that agents identify themselves; PYMNTS notes that breaching website terms can still support contract claims even if the hacking statutes do not apply. (search summary) — [PYMNTS](https://www.pymnts.com/cpi-posts/a-court-just-decided-your-ai-browser-isnt-a-hacker/); [The Fashion Law](https://www.thefashionlaw.com/can-companies-use-anti-hacking-laws-to-stop-ai-shopping-agents/)

### Inferences
- The decisive fact is architectural: requests reach Amazon from the user's own browser. A cloud-browser agent (vendor-operated browser logging in with the user's credentials) would have the vendor's computers contacting the site directly, which is closer to *Power Ventures*; the reserved-question sentence signals this. Legal exposure and technical identifiability therefore line up: the agents that can be signed and blocked (cloud) are also the ones most exposed to CFAA; the local agents are neither identifiable nor, for now, reachable by CFAA.
- The opinion pushes sites toward (a) contract enforcement against their own customers (account suspension for using unapproved agents — the "Agent Terms" approach), (b) technical blocking, and (c) non-CFAA claims (contract, trespass to chattels, unfair competition) that the court did not address. It also weakens the legal force of cease-and-desist letters as a way to revoke "authorization" for user-driven agents.
- For security analysis, the "tool of the user" framing implies the user is the legal actor for what the agent does on a site — consistent with merchant terms treating agent purchases as the customer's — while the vendor's liability for injected or mistaken actions (tort, product liability, consumer law) is explicitly left open.
- Mobile contrast: in China the norm is app/institution consent ("dual authorization", earlier notes); on Android the question is pre-empted by platform gatekeeping (privileged permission, curated allowlist). The US web answer so far is that user consent suffices as far as computer-crime law is concerned.

## 6. Browser-platform security work relevant to agents: W3C groups, agent origin isolation, passkeys/WebAuthn, Digital Credentials API

### Takeaway
The browser platform's agent-specific security work is still vendor design plus early W3C incubation: Chrome's published architecture adds Agent Origin Sets (an origin-level read / read-write allowlist per task), a metadata-only "User Alignment Critic" and mandatory confirmations for sign-in, payments and sensitive sites; W3C is moving WebMCP toward a proposed Agentic Web Working Group and has named an agent-unalterable "trusted confirmation surface" (built on WebAuthn, Secure Payment Confirmation and the Digital Credentials API) as a work item. Passkeys are the one existing web primitive an agent cannot complete on its own, because they need a user-presence gesture at the authenticator.

### Cited Findings

**Chrome's agent security architecture (Nathan Parker, Chrome Security, 8 Dec 2025)**
- *User Alignment Critic*: "a separate model built with Gemini that acts as a high-trust system component"; "architected to see only metadata about the proposed action" so that web content cannot poison it; it vets each planner action before execution. (fetched) — [Google Security blog](https://blog.google/security/architecting-security-for-agentic/)
- *Agent Origin Sets*: per task, read-only origins (content Gemini may consume — "If an iframe's origin isn't on the list, the model will not see that content") and read-writable origins where "the agent is allowed to actuate (e.g., click, type) in addition to reading from"; "a trustworthy gating function decides which origins proposed by the planner are relevant to the task". Motivation: an unrestricted compromised agent "can create what is effectively a Site Isolation bypass". (fetched) — same source
- Confirmations: before navigating to "certain sensitive sites, such as those dealing with banking transactions or personal medical information"; "before allowing Chrome to sign-in to a site via Google Password Manager"; and before "completing a purchase or payment, sending messages". "the model does not have direct access to stored passwords". (fetched) — same source
- Detection and assurance: a prompt-injection classifier that "runs in parallel to the planning model's inference" on every page the agent sees; automated red-teaming that generates malicious sandboxed sites; VRP "up to $20,000" for breaches of the agentic security boundaries. The post says nothing about the agent identifying itself to websites. (fetched) — same source
- Secondary coverage says the initial implementation tracked only the read-write set. (search summary) — [CyberInsider](https://cyberinsider.com/google-launches-new-security-architecture-for-ai-agents-in-chrome/)

**W3C**
- Web Machine Learning Community Group: publishes WebMCP (draft CG report, 13 Nov 2026). (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/)
- AI Agent Protocol Community Group: proposed May 2025; mission to develop open, interoperable protocols for agents to discover, identify and collaborate across the Web; proposed scope includes agent identity models and cross-origin communication security models (authentication, authorization, verifiable-credential-based trust); bi-weekly meetings; 2026 agendas included "W3C AC2026: the Agentic Web and the WebMCP protocol" and "DID and OAuth in the Context of the Agentic Internet". No deliverable was identified. (search summary) — [W3C group page](https://www.w3.org/groups/cg/agentprotocol); [proposal, 8 May 2025](https://www.w3.org/community/blog/2025/05/08/proposed-group-ai-agent-protocol-community-group)
- W3C/GS1 workshop "E-commerce for Humans and AI Agents" (Zurich, 8–9 Sept 2026; ~94 in person, ~80 remote; participants included Amazon, Google, Meta, OpenAI, Shopify, Visa, Stripe, PayPal) — stated W3C directions: WebMCP and agent interaction with web applications; a proposed **Agentic Web Working Group** charter (under discussion; outcomes presented at TPAC on 28 Oct 2026); co-browsing by humans and agents, including "how to tell who made a decision and who pressed the button"; a **trusted confirmation surface** building on Web Authentication, Secure Payment Confirmation and the Digital Credentials API; the Web Payments WG "may need to consider" agent identity and payment protocols. Coordination with IETF (KYA drafts, Web Bot Auth), FIDO (AP2 / Verifiable Intent / Digital Payment Credentials) and EMVCo. (fetched; draft report) — [W3C workshop report](https://www.w3.org/2026/ecommerce-agents/report.html)
- From the same report: participants "consistently wanted a confirmation step the agent cannot alter"; FIDO's position summarised as "you cannot trust the agent doing that"; a proposed "Action Acceptance" primitive asks whether an exact effect may happen now (accept / hold / refuse); FIDO's payments demo used the Digital Credentials API to show a confirmation the agent could not control; Vouched demonstrated a passkey-approved, revocable grant enforcing spend caps and product scope; OpenAI's proposed primitives include identity through OAuth, WebAuthn and passkeys; FedCM and the Digital Credentials API were suggested to avoid over-collecting personal data. The report does not discuss prompt injection explicitly. (fetched) — same source

**Passkeys / WebAuthn**
- Vendor explainers agree that an agent cannot complete a WebAuthn ceremony by itself: the authenticator requires user presence (and usually user verification — biometric or PIN), and browsers reject calls without transient user activation (`NotAllowedError`). Recommended pattern: the human authenticates with a passkey and grants the agent scoped, short-lived OAuth tokens; step-up for sensitive actions requires a fresh passkey ceremony. Reported workaround in practice: reuse cookies from a manually bootstrapped, passkey-enrolled browser profile. ChatGPT Atlas supports passkeys (human in the loop). (search summary; all vendor blogs, not the spec) — [Corbado](https://corbado.com/blog/ai-agents-passkeys); [MojoAuth](https://mojoauth.com/blog/can-an-ai-agent-complete-a-passkey-ceremony); [Corbado on Atlas](https://dev.to/corbado/chatgpt-atlas-passkey-support-current-capabilities-and-limitations-270n)
- Mastercard reports live European agentic transactions "using passkeys for authentication". (search summary) — [Mastercard Europe newsroom](https://newsroom.mastercard.com/news/europe/en/perspectives/en/2026/europe-is-building-the-foundations-for-trusted-agentic-commerce/)

### Inferences
- Agent Origin Sets are the web's counterpart to Android's per-app automation allowlist, with a different unit: *origin* (decided per task by a gating function, enforced by the browser on top of Site Isolation) instead of *package + signing certificate* (curated by Google, toggled by the user). The web version is dynamic and task-derived; the mobile version is static and vendor-curated. Both are Rule-of-Two-style narrowing of what an injected agent can reach.
- A local-browser agent holds the user's cookies for every site at once; without origin scoping, a single injection on one page can act on any logged-in origin — which is why Chrome frames the risk as a Site Isolation bypass. Origin Sets address cross-origin spread but not attacker content inside an allowed origin (reviews, messages, ads in same-origin frames).
- Passkeys change the threat picture in two ways: (1) login and step-up become a human-presence checkpoint the agent cannot script, so the agent can never itself *establish* a session — it only inherits one; (2) once the session cookie exists, the passkey gives no further protection, so agent risk concentrates in session reuse. Sites that re-prompt WebAuthn (or Secure Payment Confirmation) for high-risk actions effectively get an agent-proof confirmation today, without any new standard.
- The standards bodies have identified the same missing primitive as the research papers in the earlier notes (action-bound trusted confirmation), and are placing it in browser chrome/authenticator UI (SPC, Digital Credentials API) — the web analogue of Android Protected Confirmation or an OS-owned confirmation sheet.
- None of the platform work found gives websites a standard way to declare agent policy to the browser (e.g. "agents may read but not actuate here"); WebMCP's Permissions Policy controls only tool exposure. This remains an open slot.

### Gaps
- No Chromium design document on agent origin isolation beyond the Dec 2025 blog post was located; whether read-only sets shipped is from secondary coverage.
- Microsoft Edge (Copilot Mode), Atlas, Comet and Claude in Chrome equivalents of origin scoping were outside this note's scope (covered, if at all, by other researchers).
- Web AppSec WG work on agent-specific permissions, and any proposal for a site-declared agent policy header, were not found.
- WebAuthn spec text on agents was not read; the passkey statements come from vendor blogs. Whether any browser lets a first-party agent trigger a platform passkey prompt on the user's behalf (with the user then approving) was not verified.
- AI Agent Protocol CG deliverables and the Agentic Web WG charter text were not obtained.

## 7. Comparison points with mobile: which web mechanisms have an app-world equivalent

### Takeaway
The two worlds share the same building blocks (a structured-tool channel, an allowlist of where the agent may act, a human confirmation for money and login, and attestation of some party to the service), but the control point differs: on mobile the OS vendor curates and enforces (signed packages, privileged permissions, store policy), whereas on the open web each control is voluntary and distributed across browser vendor, agent vendor, CDN, payment network and site — and several mobile controls have no web equivalent at all.

### Cited Findings
- Unit of isolation — web: origin; WebMCP tools are same-origin by default with Permissions Policy feature `tools` defaulting to `'self'`; Chrome's Agent Origin Sets gate reading and actuation by origin. (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/); [Google Security blog](https://blog.google/security/architecting-security-for-agentic/). Mobile: Gemini's automation target list pairs package name with signing certificate, 114 apps as of 12 Nov 2026. (earlier notes, search summary) — [Android Authority](https://androidauthority.com/google-gemini-task-automation-target-apps-list-3734443)
- Structured interface — web: WebMCP callable by any attached agent, tool honesty not guaranteed ("There is no guarantee that a WebMCP tool's declared intent matches its actual behavior"). (fetched) — [WebMCP spec](https://webmachinelearning.github.io/webmcp/). Mobile: AppFunctions restricted to privileged callers, with a Play policy against manipulating agents from 14 Apr 2027. (earlier notes) — [Play Console Help](https://support.google.com/googleplay/android-developer/answer/16585319)
- Attestation to the service — web: Web Bot Auth proves key possession only ("says nothing about who operates the Agent, whether the Agent is benign, or whether the request is authorized") and does not apply to local-browser traffic. (fetched) — [datatracker](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/). Mobile: Play Integrity attests device/app integrity. (earlier notes, background) — [Android docs](https://developer.android.com/google/play/integrity)
- Who may run a GUI agent at all — web: any browser or extension; the Ninth Circuit treated a third-party agentic browser acting in the user's session as the user's own access. (fetched) — [opinion](https://www.courthousenews.com/wp-content/uploads/2026/08/amazon-v-perplexity-ninth-circuit-opinion.pdf). Mobile: Play forbids using the Accessibility API for apps that autonomously plan and execute actions; Computer Control requires a privileged permission. (earlier notes) — [Play Console Help](https://support.google.com/googleplay/android-developer/answer/16585319)
- Service-side opt-out — web: terms of service (Amazon "Agent Terms", eBay clause), server-side blocking, CDN bot rules. (search summary) — [The New Stack](https://thenewstack.io/amazon-meta-muse-block/); [ppc.land](https://ppc.land/ebay-bans-the-robot-shopper-unless-ebay-sends-the-invitation/). Mobile: no documented developer opt-out from Android Computer Control; apps rely on risk controls and `FLAG_SECURE`. (earlier notes) — [Google blog, 12 May 2026](https://blog.google/security/android-gemini-intelligence-security-privacy/)
- Trusted confirmation — web: AP2's non-agentic Trusted Surface; W3C plan for a confirmation surface on WebAuthn / SPC / Digital Credentials API; Chrome confirmations for payment and sign-in. (fetched) — [AP2 spec](https://ap2-protocol.org/ap2/specification/); [W3C workshop report](https://www.w3.org/2026/ecommerce-agents/report.html); [Google Security blog](https://blog.google/security/architecting-security-for-agentic/). Mobile: OS purchase confirmation and non-dismissable indicator; Android Protected Confirmation exists but is not wired to agents. (earlier notes)

### Inferences
Side-by-side summary (synthesis from the findings above and the earlier notes):

| Function | Web (browser agents) | Mobile (app agents) | Equivalent? |
|---|---|---|---|
| Principal / isolation unit | Origin (same-origin policy, Site Isolation) | Package + signing certificate, UID sandbox | Yes, different granularity; origins are far more numerous and unvetted |
| Where the agent may act | Agent Origin Sets — per-task, model-proposed, gated (Chrome only) | Curated allowlist of apps + user per-app toggles | Partial; web is dynamic and vendor-specific, mobile is curated |
| Structured alternative to clicking | WebMCP (origin trial), remote MCP + OAuth 2.1 profile, ACP/UCP | AppFunctions, App Intents | Yes; web lacks caller restriction and tool vetting |
| Tool/app vetting | None (site-asserted hints) | Store review, Play AppFunctions policy (2027) | **No web equivalent** |
| Who may be an agent | Anyone shipping a browser/extension; cloud browsers | OS vendor / OEM assistant; third parties barred from accessibility-based autonomy | **Opposite defaults**: open vs gated |
| Agent → service identification | Web Bot Auth (cloud agents only), UA token (voluntary), network registries (Visa/Mastercard) | None standard; service sees its own app running; Play Integrity attests app/device, not agent | Different problems; neither tells the service "an agent is driving the legitimate client" |
| Service-side refusal | ToS, server-side blocking, CDN bot rules, robots.txt (crawlers) | Risk controls, `FLAG_SECURE`, negotiation with platform; China: institutional authorization | Web sites have more unilateral technical levers; apps have a single counterparty |
| "User is present" proof | WebAuthn/passkey user-presence, SPC, 3DS | Biometric prompt, Protected Confirmation | Yes; both keep it out of the agent's reach |
| Scoped payment authority | AP2 open/closed mandates, SPT limits, agentic network tokens | Same schemes via wallet apps (AP2 lists an Android Digital Payment Credentials sample) | Shared layer, platform-neutral |
| Agent activity indicator / log | Browser-specific UI; nothing standard for the site | OS indicator, privacy-dashboard view | **No standard web equivalent** |
| Legal default (US) | User-authorized agent = user's access (9th Cir., narrow) | Not litigated; pre-empted by platform gatekeeping | — |

- Mechanisms with **no mobile equivalent**: Web Bot Auth-style self-published agent keys verified by intermediaries (CDNs); robots.txt/402 pay-per-crawl; site-level ToS enforcement against arbitrary third-party agents; an open market of agentic browsers.
- Mechanisms with **no web equivalent**: a platform owner that can deny an agent the ability to operate other parties' UIs at all; store policy on tool honesty; per-app user toggles enforced below the agent; an OS-level record of which agent touched which app.
- Security consequence: on the web, damage-bounding has to come from the browser (origin scoping, confirmations), the credential (scoped tokens/mandates, passkey step-up) and the site (its own risk controls), because there is no curator. On mobile the same bounds are mostly imposed by one actor, which is simpler to reason about but concentrates power and excludes third-party agents.
